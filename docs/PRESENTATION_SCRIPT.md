흐름: 설명(01~04) → **데모(05)** → 검증 결과(06) → 결과와 한계(07)
화면: 왼쪽 GitHub README, 오른쪽 터미널(글자 크게). 발표 전에 `sh demo.sh`를 실행해 "준비 완료"까지 띄워 둔다.
`[엔터]`는 데모 구간에서만 쓴다. 엔터 6번이 `demo.sh`의 멈춤 6번과 정확히 맞는다.

#### [표지] 0:00 – 0:15

안녕하세요. "HTTP는 Stateless인데, 서버는 어떻게 나를 기억할까?"를 주제로 발표하겠습니다.

이번 주에 C로 만든 웹 서버의 소켓, HTTP, 동시성, 프록시를, **로그인 상태 유지**라는 시나리오로 검증했습니다.

#### [01 웹 서버 프로젝트] 0:15 – 0:30

이 그림은 요청 하나가 서버 안을 지나가는 길입니다.

연결을 받으면 작업 스레드가 요청을 읽고, 쿠키로 Session을 찾은 뒤 응답을 보냅니다.

오늘 다룰 문제는 모두 이 길 위의 빨간 상자에서 생겼습니다.

#### [02 문제 정의] 0:30 – 0:55

HTTP는 요청마다 독립적이라, 방금 로그인한 사용자도 다음 요청에서는 알아보지 못합니다.

로그인을 유지하려면 세 가지 질문에 답해야 합니다.

첫째, 사람을 무엇으로 구분할까.

둘째, 언제 잊고, 어떻게 안전하게 지울까.

셋째, 서버가 늘어나도 같은 사람으로 알아볼까.

#### [03 소켓 — 연결은 사라진다] 0:55 – 1:05

첫째, 가장 먼저 떠오른 식별자는 소켓 FD였지만, 커널은 닫힌 FD 번호를 다음 연결에 바로 다시 줍니다.

그래서 쿠키에 담긴 Session ID로 사용자를 구분하는, 서버 측 Session을 택했습니다.

#### [03 HTTP와 타이머] 1:05 – 1:30

둘째, 언제 잊을지입니다. Idle Timeout과 Absolute Timeout을 함께 두었습니다.

요청이 없어도 만료를 정리해야 합니다. epoll 같은 이벤트 루프라면 타이머를 루프에 두겠지만, 비밀번호 해싱 같은 느린 작업이 루프를 멈춥니다.

그래서 스레드 풀을 유지하고, 1초마다 깨어나는 accept 루프를 타이머로 썼습니다.

#### [04 스레드 풀 — 공유 메모리] 1:30 – 1:55

그럼 어떻게 안전하게 지울까요. 첫 번째 그림처럼, 한 스레드가 포인터로 응답을 만드는 사이 다른 스레드가 메모리를 해제하면 Use-After-Free가 발생합니다.

두 번째 그림의 넓은 락처럼 응답까지 락을 쥐면 안전하지만, 다른 스레드가 모두 기다립니다.

그래서 좁은 락으로, 값만 복사하고 바로 락을 풀었습니다.

#### [05 데모] 1:55 – 2:55

이 선택들이 실제로 맞는지, 데모로 확인해 보겠습니다.

`[엔터]` 첫 번째는 HTTP와 쿠키입니다. 로그인하면 쿠키로 Session ID를 받습니다.

`[엔터]` 새 연결로 요청해도 userA로 인식되고, 쿠키가 없거나 위조하면 401입니다.

`[엔터]` 두 번째는 소켓입니다. 서버 로그를 보면 세 연결이 모두 fd 5를 받았습니다.

Session 방식에서 로그인하지 않은 B는 401입니다.

그런데 FD 방식에서는, 서버가 B를 userA로 착각했습니다.

B는 아무것도 보내지 않았는데 말입니다.

`[엔터]` 세 번째는 스레드 풀의 Use-After-Free입니다. 포인터를 넘기는 버전은 AddressSanitizer가 바로 검출합니다.

`[엔터]` 값을 복사하는 버전은 0건입니다.

`[엔터]` 마지막으로 인증 테스트 6개가 모두 통과합니다.

#### [06 검증] 2:55 – 3:25

AI로 빠르게 구현한 만큼, 생성된 코드를 믿지 않고 세 단계로 확인했습니다.

첫 번째 표처럼, 테스트와 새니타이저 3종을 모두 통과했습니다.

예상과 다른 결과도 있었습니다. TSan은 방금 본 UAF를 잡지 못했고, 좁은 락은 동시성 8에서만 빨랐습니다. 50에서는 병목이 스레드 풀로 옮겨 갔기 때문입니다.

마지막 표는 데이터 레이스나 느린 요청처럼, 테스트가 먼저 잡아낸 문제들입니다.

#### [07 Reverse Proxy · 결론] 3:25 – 3:55

셋째, 서버를 두 대로 늘리자, 같은 쿠키로도 200과 401이 번갈아 나왔습니다. Session이 각 서버 메모리에만 있기 때문입니다.

로그인 하나를 붙였을 뿐인데, 웹 서버의 연결 수명, 공유 메모리, 프록시 뒤의 여러 서버가 모두 문제로 드러났습니다.

기술 선택은 서비스의 요구사항과 Trade-off로 결정된다는 것을 배웠습니다. 감사합니다.

## 예상 질문

**왜 HTTPS를 쓰지 않았나요?**
말씀하신 대로 지금은 쿠키와 비밀번호가 평문으로 전송되므로, 실서비스라면 HTTPS는 필수입니다. 다만 이번에는 전송 구간이 아니라 서버가 사용자를 기억하고 잊는 문제에 집중했습니다. TLS를 적용해도 FD 재사용, 만료, UAF 문제는 남고, 이미 유출된 Session ID의 재사용도 막지 못합니다. 그래서 범위에서 제외하고 한계로 명시했습니다.

**테스트가 통과하는 게 우연이 아니라는 건 어떻게 아나요?**
수정마다 회귀 테스트를 추가하고, 수정 전 코드에서 그 테스트가 실패하는 것을 먼저 확인했습니다.

**AI가 만든 코드를 어떻게 믿었나요?**
믿지 않는 것을 전제로 했습니다. 단위·기능 테스트, 새니타이저 3종, Linux 환경 검증, 수정 전후 성능 비교를 거쳤고, README 06의 표에 있는 문제들은 모두 이 과정에서 발견했습니다.
