## 핵심 개념 정리

### HTTP 요청 모양과 파싱이 어려운 이유
- 구조: 요청 라인(`메서드 URI 버전`) → 헤더(`이름: 값`) 여러 줄 → 빈 줄 → 본문
- 줄 끝 = `\r\n`. 헤더 끝 = `\r\n\r\n`. 본문 길이는 `Content-Length`로 판단
- TCP = 바이트 스트림이라 메시지 경계 없음. recv 한 번에 반만 오거나 두 요청이 붙어 올 수 있음
  - 헤더 끝 = `\r\n\r\n`
  - 본문 끝 = 헤더 끝 + CL 바이트

### 제자리(in-place) 파싱
```
전: GET /a HTTP/1.1\r\nHost: x\r\n
후: GET\0/a\0HTTP/1.1\0\nHost\0 x\0\n
```
- 장점: 복사 없음, malloc 없음, 누수 불가
- 단점: 구조체 포인터는 원본 버퍼가 살아 있는 동안만 유효
- 검증이 다 끝난 뒤에 `'\0'`을 씀 (`*sp1 = *sp2 = *eol = '\0'`)

### 파서 흐름 (`http_parse_request`)
1. 사전 검사: `\r\n\r\n`으로 끝나는지, 헤더 안 NUL 바이트 없는지 → 아니면 400
2. `find_eol`: CRLF만 줄바꿈 인정. 단독 `\r`/`\n` → 400
3. `parse_request_line`: 메서드(token 문자만), URI(`/` 또는 `http://` 시작, 2048 초과 414), 버전(`HTTP/d.d`, 1.0/1.1 아니면 505)
4. `parse_header_line` 반복 (빈 줄까지): 공백 시작 줄(obs-fold) 400, 콜론 앞 공백 400, 값 앞뒤 공백 제거, 64개 초과 431
5. 의미 검사: Host 중복 400, CL 서로 다른 값 중복 400, `parse_content_length` 숫자만+오버플로 검사, TE 있으면 501
6. keep-alive 결정
- **판정 순서**: 문법 400 → 버전 505 → Host 필수 400 → TE/메서드 501. 예: Host 없는 PUT = 400 (501 아님)
- 직접 구현 이유: `tolower` 대신 자체 → locale 영향 회피. `strtol` 대신 자체 → `"+5"`, `" 5"` 허용 막음. 오버플로는 곱하기 **전에** 검사

### 오류 코드 표
| 코드 | 언제 |
|---|---|
| 400 | 문법 오류, Host 중복/누락(1.1), CL 충돌 |
| 411 | POST인데 CL 없음 |
| 413 | 본문 1MB 초과 |
| 414 | URI 2048바이트 초과 |
| 417 | `Expect`가 `100-continue` 아님 |
| 431 | 헤더 64개 초과 / 헤더가 버퍼(8KB) 넘침 |
| 500 | malloc 실패 |
| 501 | GET/POST 외 메서드, Transfer-Encoding |
| 505 | HTTP/1.0·1.1 아닌 버전 |

### keep-alive 결정
- 1.1 기본 유지, 1.0 기본 종료, `close` 토큰 있으면 무조건 종료
- `Connection: Upgrade, Close` 같은 쉼표 목록도 `has_token`으로 처리. `closed`처럼 일부만 같은 값은 불일치
- 지금은 파싱만 함. 응답은 항상 `Connection: close`

### 요청 스머글링 (엄격 거절 이유)
- 프록시와 백엔드가 같은 요청을 다르게 해석하면 요청 하나 안에 다른 요청을 숨길 수 있음
- 예: CL 5와 6이 같이 오면 어느 쪽을 믿느냐에 따라 본문 경계가 달라짐 → 400

### 본문 수신 (`http_read_body`)
1. Expect가 `100-continue` 아니면 417 (HTTP/1.1만 검사)
2. POST + CL 없음 → 411 (GET은 본문 없음으로 통과)
3. CL > 1MB → 413. **100 Continue 보내기 전에 판정** → 클라가 큰 본문을 헛되이 안 보냄
4. 이미 다 받았으면 버퍼 안을 그대로 가리킴 (recv 추가 없음)
5. 하나도 안 받았고 Expect 있으면 `100 Continue` 전송 (curl은 1KB 넘는 POST에서 이걸 기다림)
6. `header_len + cl < cap`이면 헤더 버퍼에 이어 받기, 아니면 `malloc(cl+1)` → `heap_out`으로 반환, 호출자가 `free`
7. `tcp_recv_exact`로 남은 바이트만 받음 → 파이프라이닝 다음 요청은 안 먹음
- 반환: 0 / -1(끊김·타임아웃 → 응답 없이 닫기) / 411·413·417·500

### 연결 끊김 감지 (ECONNRESET)
- 끊김 전용 API 없음. 다음 `recv`/`send`/`poll` 결과로 알게 됨. 커널은 FIN/RST가 도착해야 앎
| 상대 행동 | 패킷 | 내 쪽 결과 |
|---|---|---|
| 정상 close | FIN | `recv` → 0 (EOF) |
| 안 읽은 데이터 남기고 close / 닫힌 소켓에 내가 send | RST | -1, `ECONNRESET` |
| FIN 받은 뒤 계속 send | 이후 RST | `send` -1, `EPIPE` (SIGPIPE 무시 중이라서) |
- `poll`: `POLLHUP`/`POLLERR` (Linux는 `POLLRDHUP`로 half-close). 정확한 이유는 다음 recv/send에서 나옴
- 함정: 랜선 뽑힘·전원 꺼짐 → FIN도 RST도 안 옴 → recv 영원히 블록. **마감 시간(timeout)이 유일한 방어**
- 오래 유지하는 연결이면 `SO_KEEPALIVE` + `TCP_KEEPIDLE/INTVL/CNT` (기본 2시간이라 줄여 써야 함)
- 재현: `printf 'GET / HTTP/1.1\r\n' | nc -q0 localhost 8080` → 헤더 도중 FIN → 400 로그. RST는 `SO_LINGER {1,0}` 후 close

### GET/POST 구분과 응답 경로
- 구분: `parse_request_line()` 끝 `strcmp(line, "GET")`, `"POST"`, 나머지 `OTHER`. 대소문자 구분 → `get`은 OTHER
- 사용처: `OTHER` → 501 (`http_parser.c`, 문법 검사 이후), POST + CL 없음 → 411 (`http_body.c`)
- 응답은 파서가 아니라 `main.c handle_client()`가 결과 보고 보냄
```
handle_client
 ├ http_parse_request ─ rc≠0 → send_error(rc)
 ├ http_read_body ─ -1 → close / rc>0 → send_error(rc)
 └ send_echo (GET/POST 같은 처리)
send_error / send_echo → http_format_head → send_resp → tcp_send_all
```
- 보낸 뒤: 0 반환 → `tcp_close_graceful` (RST 방지), -1 → 바로 `close`
- 메서드별 처리는 나중에 `send_echo` 자리에서 `switch (req.method)` (예: 정적 파일은 GET만, POST는 405)

### 응답 머리 (`http_response`)
- `http_reason()`: 코드 → 이유 문구 표 (다음 단계용 403/404/502/504 포함, 모르는 코드 `"Unknown"`)
- `http_format_head()`: 상태 줄 + Content-Type/Content-Length/Connection + 빈 줄. 버퍼 모자라면 -1 → 잘린 응답 안 보냄
- 오류 응답 예:
```
HTTP/1.1 400 Bad Request\r\n
Content-Type: text/plain; charset=utf-8\r\n
Content-Length: 16\r\n
Connection: close\r\n
\r\n
400 Bad Request\n
```
