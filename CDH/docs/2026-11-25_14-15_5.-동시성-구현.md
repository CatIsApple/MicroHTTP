## 핵심 개념 정리

### 동시성 모델 선택
| 모델                | 장점                                            | 단점                                                  | 판정     |
| ----------------- | --------------------------------------------- | --------------------------------------------------- | ------ |
| 요청당 `fork`        | 격리, 단순                                        | 프로세스 비용, keep-alive 비쌈                              | ✗      |
| 연결당 스레드           | 코드 그대로                                        | 스레드 수 무제한 → 메모리 폭탄                                  | ✗      |
| 스레드 풀 (5a)        | 블로킹+마감 코드 재사용, `getaddrinfo`/`connect` 블로킹 OK | 쉬는 keep-alive 연결이 워커 점유 → C10K 약함                   | 5a     |
| epoll 이벤트 루프      | C10K                                          | 파서·본문·sendfile·drain·프록시 전부 상태 머신 재작성. epoll 리눅스 전용 | ✗      |
| 풀 + 쉬는 연결 감시 (5b) | 쉬는 연결은 epoll, 일하는 연결만 워커                      | 코드 조금 더                                             | **채택** |
- 5a = Apache **worker** MPM, 5b = Apache **event** MPM, 전부 epoll 상태 머신 = nginx.
- 5a/5b는 내가 붙인 이름: 5a 먼저 → 측정 → 5b 붙이고 재측정 → 개선이 숫자로 보이게. (사용자 결정: 5b로 바로)

### C10K
- 정의: 동시 연결 1만 개 문제 (Dan Kegel, 1999).
- 연결당 프로세스/스레드 → 1만 개면 메모리·문맥 교환 폭발 (스택 8MB × 1만 = 가상 80GB).
- `select` fd 1024 제한 + O(n), `poll` O(n), **epoll/kqueue = O(준비된 수)**.
- 핵심: 연결 대부분은 쉬는 중 → 쉬는 연결은 커널 이벤트 통지에, 데이터 온 연결만 일꾼이 처리.
- 요즘은 C10M → DPDK(커널 우회), io_uring.

### Apache MPM / event MPM vs nginx
- MPM = Multi-Processing Module, 동시성 모델 플러그인. prefork(프로세스=연결) / worker(스레드=연결) / event(worker + 쉬는 연결을 리스너 스레드 epoll에 넘김).
- 근본 차이 = **"누가 기다리나"**. nginx는 커널(epoll)만 기다림, event MPM은 일하는 도중엔 스레드가 기다림.
- nginx: 요청 처리도 논블로킹 상태 머신, 워커 = 코어 수, 문맥 교환 거의 없음.
- event MPM: 읽기·처리는 블로킹, 쉬는 구간·일부 쓰기(2.4 비동기 쓰기)만 비동기.
- 성능 경향:
  - 정적 RPS·연결 수만·느린 클라·프록시 앞단 → nginx 우세 (`open_file_cache`, `.htaccess` 없음, `proxy_buffering`)
  - PHP-FPM 뒤 동적 처리 → 비슷 (병목 = 백엔드)
  - 장애 격리·블로킹 모듈 작성 쉬움 → Apache (nginx는 블로킹 한 줄 = 워커의 연결 수천 개 멈춤)
- 타임아웃: nginx = 레드블랙 트리 O(log n). MPM listener = keep-alive 큐(같은 타임아웃이라 FIFO).
- 5b 약점 = 읽기 블로킹(slowloris가 워커 점유, 마감 5초로 묶음), 프록시 버퍼링 없음.
- 헷갈렸던 점: "그럼 무조건 nginx가 좋은 거 아냐?" → **아님**. 대가:
  1. 코드가 상태 머신 (`switch(conn->state)`), 증분 파서, 지역 변수 → 구조체, 조합 폭발 버그
  2. 블로킹 호출 하나 = 전부 멈춤 (nginx는 비동기 DNS, `aio threads`까지 만듦)
  3. CPU 무거운 일에 약함 → nginx는 프록시라 가능한 구조
  4. 디버깅 어려움 (스택에 흐름 안 남음)
  - 업계 방향: 사람은 블로킹으로 쓰고 런타임이 이벤트로 바꿈 (Go goroutine, Java 21 가상 스레드, async/await). C엔 그런 런타임 없음.
  - 과제에서 5b 이유: 연결 수백~수천이면 충분, CGI/프록시의 블로킹 호출 많음, 기존 코드 재사용.

### epoll 분배 방식 / IOCP 대응
- IOCP처럼 하려면 gateway 불필요: **공유 epoll + `EPOLLONESHOT`** → 커널이 이벤트 하나를 워커 하나에만. 유저 락 0. listen fd는 `EPOLLEXCLUSIVE`/`SO_REUSEPORT`로 thundering herd 방지.
- gateway 유지 시: 워커별 **SPSC 링 + eventfd** (head/tail atomic, acquire/release). 잠든 워커 깨우기는 결국 시스템콜.
- 제일 쉬움: **워커별 epoll** + gateway가 `epoll_ctl(epfd[i], ADD)`.
- 사용자 IOCP 경험(소켓마다 전용 스레드) = 워커별 epoll + 연결 고정. `ONESHOT` 불필요, 연결 상태 락 불필요, 캐시 지역성 좋음. 단 쏠림, **블로킹 금지 → 논블로킹 상태 머신 재작성 필요**. gateway도 없애려면 `SO_REUSEPORT`.
- 5b vs 워커별 epoll: 5b = 워커가 요청 1개, 매 요청 아무 워커, 블로킹 OK, 공유 큐 자동 분산, 넘기기 비용(큐+깨우기). 워커별 epoll = 연결 수백 개, 고정, 넘기기 없음, 블로킹 하나 치명적.
- "락 없음"은 유저 공간 기준. 커널 안엔 락 있음.
- epoll = **준비 통지**(읽기는 내가), IOCP = **완료 통지**(커널이 읽어 둠).

### 논블로킹이 안 먹는 블로킹 작업
| 작업 | 이유 | 단계 |
|---|---|---|
| `getaddrinfo` | POSIX 논블로킹 버전 없음 | Forward Proxy |
| `open`/`openat`/`fstat` | 디스크 파일엔 `O_NONBLOCK` 무효 | 정적 파일 |
| `sendfile`/`pread` (캐시 미스) | 디스크 읽기 대기 | 정적 파일 |
| `fork`/`exec`/`waitpid` | 메모리 복사, 출력 대기 | CGI |
| `connect` | `EINPROGRESS`+`EPOLLOUT` 직접 처리 안 하면 블로킹 | Reverse Proxy |
| `printf` | stdout 가득 차면 막힘 | 로그 |
| `wait_until`(poll) | 마감까지 일부러 잠듦 | 현재 전부 |
- 스레드 풀: 그냥 호출 OK (워커 하나만 멈춤). 이벤트 루프: 별도 블로킹 스레드 풀 + eventfd 알림(nginx `thread_pool`, libuv) 필요 → 결국 둘 다 만듦.
- epoll은 소켓·pipe 전용, 파일 비동기는 `io_uring` 필요.

### io_uring
- 리눅스 5.1+ **완료 통지** 비동기 I/O = 리눅스판 IOCP.
- SQ(제출 큐) / CQ(완료 큐) 둘 다 mmap 공유 메모리 → 넣고 빼는 데 시스템콜 없음, `io_uring_enter` 한 번에 묶음. `SQPOLL`이면 0번.
- 대응: SQE = overlapped 요청, CQE = 완료 패킷, user_data = completion key.
- 파일·open·stat·connect·accept 대부분 지원.
- 과제: liburing은 "이벤트 루프 라이브러리 금지" 회색 지대, macOS 없음, Docker 등 기본 차단 → 본 구현 비추. 하려면 `#ifdef __linux__` 선택 백엔드.

### TSan (ThreadSanitizer)
- `-fsanitize=thread`. **데이터 경쟁** 탐지: 같은 메모리에 동시 접근 + 하나 이상 쓰기 + 동기화 없음.
- 메모리 접근마다 벡터 시계 기록, mutex/create/join/atomic의 happens-before 추적 → 관계 없으면 보고 (두 스택 같이 출력).
- 운 좋게 결과 맞아도 동기화 빠지면 잡음. 단 **실행된 경로만** → 테스트 반복 실행 필요.
- ASan(오버플로·UAF·누수, ~2배) vs TSan(경쟁·락 순서, 5~15배). **같이 못 씀** → `make tsan` 별도 타깃.
- `volatile sig_atomic_t`는 시그널용, 스레드 동기화 아님.
- WSL: ASLR 켜져 있으면 "unexpected memory mapping"으로 죽음 → `setarch $(uname -m) -R`.

### 멀티 프로세스 vs 멀티 스레드
| | 프로세스 (`fork`) | 스레드 |
|---|---|---|
| 메모리 | 분리 (COW) | 공유 |
| 생성 | 50~200µs | 5~20µs |
| 단위 메모리 | 수백KB~MB | 수십KB |
| 데이터 공유 | IPC 번거로움 | 그냥 메모리 + 락 |
| 장애 격리 | 하나 죽어도 나머지 삶 | segfault 하나에 전체 죽음 |
| 버그 | 레이스 적음 | 경쟁·데드락 (TSan) |
| 보안 | 권한 분리 가능 | 같은 권한 |
- 요청마다 fork → 수 배~10배 느림(CGI 느린 이유). 풀로 쓰면 처리량 차이 작음, 차이는 메모리·공유 방식.
- 연결 하나가 단위 하나를 잡으면 둘 다 C10K 한계 → 이벤트 루프 필요.
- 추천: 과제는 5b 그대로(문서 루트 fd, 프록시 카운터 공유 쉬움). 실무 최고는 프로세스=코어 수 × 이벤트 루프 + `SO_REUSEPORT`.
- 보고서 아이디어: `-m fork` 모드 추가해 fork / 풀 / 풀+idle poller 3종 비교표.

### CGI / FastCGI / PHP-FPM / PHP
- **CGI** (RFC 3875): 요청마다 `fork`→`exec` 외부 프로그램. 요청 정보 = 환경변수(`REQUEST_METHOD`, `QUERY_STRING`, `HTTP_*`), POST 본문 = stdin, 응답 = stdout.
  - 구현: `pipe` 2개 → `fork` → `dup2` → `execve`, 부모는 마감 있게 read + `waitpid`(좀비 방지). 없음 404 / 실패 500 / 오래 → kill + 504.
  - 멀티스레드 fork 주의: 호출 스레드만 복제, fork~exec 사이 async-signal-safe만 → `posix_spawn` 추천. `SOCK_CLOEXEC` 이미 됨.
- CGI 느린 이유: fork + exec + 인터프리터 초기화 + 컴파일 + DB 연결을 매번. 진짜 일 1ms, 준비 10~50ms.
- **FastCGI**: 프로세스 미리 띄워 재사용. 내용은 CGI와 같고 **전달 수단만 소켓 위 이진 메시지**로.
  - 메시지 = 8바이트 머리 `version|type|requestId(2)|contentLength(2)|paddingLength|reserved` + 내용 + padding.
  - 흐름: BEGIN_REQUEST → PARAMS… → 빈 PARAMS → STDIN… → 빈 STDIN → STDOUT… → END_REQUEST.
  - PARAMS 이름-값은 length-prefixed (`0E 04 REQUEST_METHOD POST`) → `=`·`\0` 섞여도 안전.
  - 텍스트(구분자 검색, strtol) vs 이진(길이 필드로 경계 바로). TCP는 경계 없는 바이트 스트림 → 길이 필드가 경계. HTTP/2, gRPC도 같은 프레임 방식.
- **PHP-FPM**: PHP용 FastCGI 서버. master(root)가 워커 fork·재시작, 워커들이 같은 리스닝 소켓에서 accept (큐 불필요).
  - `pm`: static / dynamic(기본) / ondemand. `max_children`(메모리 상한), `max_requests`(누수 대비 재시작), `request_terminate_timeout`, `request_slowlog_timeout`, `listen.backlog`.
  - 재사용 이득: OPcache, 영구 DB 연결, 초기화 1번. 그래도 요청 끝나면 전역 상태 지움(**shared-nothing**).
  - 역사: CGI → mod_php(Apache prefork에 내장, 정적 요청도 무거운 프로세스) → PHP-FPM(웹서버와 분리).
  - 우리 서버 대응: 워커 풀 ↔ `-t N`, backlog ↔ 큐+503, `max_requests` ↔ `keepalive_max`, nginx 쉬는 연결 ↔ idle poller, nginx↔FPM ↔ Reverse Proxy 단계.
- **PHP**: 서버 쪽 스크립트 언어(1994, Rasmus Lerdorf). HTML 안 `<?php ?>`. `$_GET`/`$_POST` = CGI 환경변수·stdin을 언어가 풀어 준 것. 배포 쉬움, WordPress·MediaWiki. PHP 7 속도 2배, PHP 8 JIT. 우리 서버 입장에선 CGI/FastCGI로 붙이는 외부 프로그램 중 하나.

### idle poller 구조 (`src/idle_poller.c`)
- 역할: keep-alive로 **쉬는 연결**을 맡아 보는 스레드 1개. 워커가 쉬는 연결 붙잡고 기다리지 않게.
- 부품: `idle_entry`(job + 마감 시각 + 리스트 링크), 대기열 `pend_*` + `mu`(락 필요한 건 여기뿐), wake pipe, 감시 리스트 `head/tail`(감시 스레드 전용, 락 없음), `epfd`/`pfds`(epoll / poll).
- 함수:
  - `idle_park`: 아무 스레드. `mu` 안에서 `max_conns`·stopping 확인 → 대기열 끝에 붙이고 마감 기록 → 대기열 비어 있었을 때만 wake. 실패 시 fd 안 건드림(호출자가 닫음).
  - `poller_main`: `expire` → `epoll_wait` → `handle_ready` → (wake면) `drain_wake` + `take_pending`.
  - `handle_ready`: `epoll DEL` → 리스트에서 빼기 → free → **락 없이** `ready_fn`. 넘긴 뒤 fd는 남의 것이라 감시부터 해제.
  - `expire`: 맨 앞만 봄.
  - `idle_stop`: stopping → wake → join → 남은 fd close → `inflight` 0까지 대기 → free.
- 설계 이유:
  - 타임아웃 O(1): 모든 연결 제한 시간 같음 → park 순서 = 마감 순서 → FIFO 리스트, 맨 앞만.
  - 감시 스레드는 recv 안 함 (다음 요청 바이트 먹으면 안 됨).
  - `EPOLLRDHUP`: FIN도 깨움.
  - wake를 `mu` 안에서 씀 → `idle_stop`의 pipe close와 경쟁 없음.
  - `ready_fn` 락 밖 → 콜백 안 재-park해도 교착 없음.
  - SIGINT/SIGTERM 막고 스레드 생성 → 시그널은 main(accept)만.
  - poll 백엔드: macOS용, 매 루프 pollfd 재구성 O(n).
- 한계: `idle_stop` free 후 `idle_park` = UAF → 종료 순서 `tp_shutdown` → `idle_stop` → `tp_destroy` 고정. `inflight` 대기 1ms 바쁜 대기.

### 전체 플로우 (함수 이름)
```
[준비] main: install_signal_handlers → static_open_root → tcp_listen
       → tp_create(tp_worker × N 잠듦) → idle_create(poller_main 잠듦)
[연결 옴] tcp_accept → tp_submit ──(가득)──▶ reject_busy (503 → close)
[워커] tp_worker → serve_connection → handle_request (반복)
         tcp_recv_request → http_parse_request → http_read_body
         → send_echo(POST) / serve_static(GET/HEAD: static_lookup → http_send_response)
       handle_request 반환:
         CONN_GRACEFUL → tcp_close_graceful (끝)
         CONN_ABORT    → close (끝)
         CONN_KEEP → 잔여 있음 / PEEK 데이터 → handle_request
                     PEEK 0(FIN) → close
                     EAGAIN → idle_park → wake (워커 반환)
[감시] poller_main: expire(5초 → close) / epoll_wait / drain_wake → take_pending
       / handle_ready → server_on_idle_ready → tp_submit → 워커로
[종료] on_shutdown_signal → tp_shutdown → idle_stop → tp_destroy
```
- 헷갈렸던 점: 플로우를 `idle_create`부터 썼음 → "오는 거부터 해야지" → 연결 도착 순으로 다시.
- 헷갈렸던 점: "keep 아님"이 `serve_connection`에 없음 → 맞음. `keep`은 `handle_request` 안 지역 변수, `serve_connection`은 `CONN_*` 반환값만 받음.

### `keep` (keep-alive 판단, `server.c` handle_request)
전부 참이어야 1:
| 조건 | 코드 | 거짓 |
|---|---|---|
| 클라가 원함 | `req.keep_alive` | `Connection: close`, HTTP/1.0 헤더 없음 |
| 요청 수 상한 | `nreq + 1 < keepalive_max` (100) | 100번째 |
| 종료 중 아님 | `!tp_stopping` | Ctrl+C |
| 안 바쁨 | `queued*4 < capacity*3` | 큐 75% 초과 → 워커 양보 |
| 정상 응답 | `serve_static`/`send_echo`가 `*keep=0` | 500 등 |
- 400·411·413·431 등 요청 자체 오류는 계산 전 `error_and_close` (요청 경계 신뢰 불가).
- **응답 보내기 전**에 결정 → `Connection:` 헤더와 실제 동작 일치.
- 404/403/301은 요청 다 읽은 정상 응답이라 keep 유지 (nginx와 같음, 이번에 수정).

### 감시 스레드가 왜 필요한가 (cond만으론 안 되는 이유)
- 내 이해: 큐에 넣으면 cond로 워커 깨우는데 감시 스레드는 왜? → 실제: 문제는 **누가 큐에 넣느냐**.
  - 새 연결 → `accept`가 알아챔 → main이 `tp_submit`.
  - 쉬던 연결에 다음 요청 → **커널 사건**이라 cond는 모름 → 소켓을 지켜볼 누군가 필요 = 감시 스레드.
- 없으면: 워커 16개가 쉬는 연결 16개 recv에서 잠듦 → 새 연결 깨울 워커 없음.
- 감시 스레드 = "소켓 읽기 가능"(커널) → "큐에 작업"(cond) 다리.
- 감시 스레드는 `epoll_wait`에서 자서 cond 못 기다림 → park 시 pipe 1바이트로 깨움.
```
워커 ──cond──▶ 잠든 워커        (큐에 작업)
워커 ──pipe──▶ 잠든 감시 스레드  (감시할 연결 추가)
커널 ──epoll─▶ 잠든 감시 스레드  (데이터 옴 / 타임아웃)
```
- 비유: 워커 = 요리사, 감시 스레드 = 홀 직원(여러 테이블 혼자 봄, 추가 주문 → 주방에 주문서(큐), 오래 조용 → 내보냄).
- 위치:
  - 넘기기 `idle_park`: 호출 `server.c:292`, 정의 `idle_poller.c:385`, wake `:425`
  - epoll: `poller_main` `epoll_wait` `idle_poller.c:237`, `take_pending` `epoll_ctl(ADD)` `:194`, `handle_ready` `:250`
  - 깨우기: `handle_ready`(`:174` ip->fn) → `server_on_idle_ready`(`server.c:302` tp_submit) → `tp_submit`(`thread_pool.c:198` cond_signal) → `tp_worker`(`:58` cond_wait, `:70` fn)
- 확인: "최종적으로 워커 깨우는 건 tp_submit의 큐 push + cond_signal?" → **ㅇㅇ, 유일한 길**. 호출처 2곳: main(`main.c:221`), 감시 스레드(`server.c:302`). 잠든 워커 없으면 signal 헛방이지만 job은 큐에 남고, 일 끝낸 워커가 `count > 0` 보고 바로 꺼냄(`thread_pool.c:57`).
- (줄 번호는 주석 채우기 전 기준)

### `ip->stopping`
- idle poller 종료 플래그 (`atomic_int`). 켜는 곳: `idle_stop`이 `mu` 잡고 1.
- 읽는 곳: 감시 루프 `while(!stopping)`, `idle_park` 락 없이 빠른 거절, `idle_park` `mu` 안 최종 판단.
- 역할: ① 무한 루프 감시 스레드 멈춤 (stopping=1 → wake → 루프 탈출 → join) ② 종료 중 새 park 거절 (`-1/ECANCELED`, 호출자가 close) → fd 누수 방지.
- `mu` 안에서 켜는 이유: park(확인+넣기)와 stop이 같은 락 → 둘 중 하나만. park 먼저면 stop이 대기열 fd까지 close, stop 먼저면 park 거절. fd 누수·이중 close 없음.
- `tp->stopping`도 같은 패턴.
- 비유: "가게 문 닫는 중" 팻말.

### `pipe()` / self-pipe trick
- 커널 안 한 방향 바이트 통로. `p[0]` 읽기, `p[1]` 쓰기. 버퍼 64KB.
- 비면 read 막힘, 가득이면 write 막힘(논블로킹이면 EAGAIN), 쓰는 쪽 다 닫으면 read 0(EOF), 읽는 쪽 다 닫고 쓰면 SIGPIPE/EPIPE.
- **그냥 fd라 poll/epoll에 넣을 수 있음** ← 핵심. 원래 용도 = 프로세스 간 통신(`ls | grep`, CGI).
- self-pipe trick: wake_r을 epoll에 등록(`data.ptr = NULL`), 깨우려면 wake_w에 1바이트.
  - `wake`: EAGAIN 무시(이미 깨울 바이트 있음). `drain_wake`: 다 비움(레벨 트리거라 안 비우면 계속 깸).
  - thread_pool의 wake pipe는 종료 알림용이라 **일부러 안 비움** → 누가 poll해도 즉시 깸.
- 논블로킹 이유: 쓰는 쪽은 `mu` 잡은 채 wake → 막히면 교착. 읽는 쪽은 "빌 때까지 읽기"라 블로킹이면 영원히 잠듦.
- eventfd가 더 가볍지만 리눅스 전용 → 이식성 위해 pipe.
- `mu` = mutex(`pthread_mutex_t`), 대기열 같은 공유 데이터 보호.

### Concurrency vs Parallelism
- 동시성 = **concurrency** (concurrent). 겹쳐서 진행, 코어 1개라도 됨 (idle poller 하나가 1만 연결).
- 병렬성 = **parallelism**. 실제 같은 순간 실행, 코어 여러 개 (워커 16개).
- 5단계 이름: "concurrency model" / "concurrent request handling".
