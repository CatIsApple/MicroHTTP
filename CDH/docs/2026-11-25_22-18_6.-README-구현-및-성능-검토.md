## 핵심 개념 정리

### 리버스 프록시 vs 포워드 프록시
- **리버스:** 서버 앞의 대리 창구.
  - 손님은 8080만 앎. 8080이 경로를 보고 뒷단에 대신 전달하고, 응답을 받아 돌려줌.
  - 목적지는 **운영자**가 정함(`-P`). 손님은 프록시 존재를 모름.
- **포워드:** 클라이언트 쪽 대리인.
  - 손님이 "example.com 가줘" 하면 대신 감. 목적지는 **손님**이 고름.
  - 손님이 프록시 사용을 알고 직접 설정함(브라우저 설정, `curl -x`).
- **요청 모양 차이:**
  - 포워드: `GET http://example.com/a HTTP/1.1` (absolute-form)
  - 일반·리버스: `GET /a HTTP/1.1` (origin-form)
  - HTTPS 포워드: `CONNECT example.com:443` (authority-form) → 바이트 터널

| | 포워드 | 리버스 |
|---|---|---|
| 누구를 대신하나 | 클라이언트 | 서버 |
| 존재를 아는 쪽 | 클라이언트 | 모름 |
| 목적지 | 요청 URL의 아무 서버 | 미리 정한 백엔드 목록 |
| 쓰임 | 회사 망 출구, 차단, 캐싱, 익명화 | 로드밸런싱, 서버 보호 |

- **헷갈렸던 점 1:** 내 이해 "`-P`에 다른 URL 넣으면 손님이 원하는 다른 서버로 감" → 실제: 그건 리버스. 손님이 목적지를 고르는 건 포워드. 내가 원래 말한 건 포워드였음.
- **헷갈렸던 점 2:** 내 이해 "지금 프록시는 내 서버 1개로 넘어감" → 실제: `-P`가 없으면 프록시 꺼짐. 넘기지 않고 직접 응답함.
- **헷갈렸던 점 3:** 내 이해 "프록시 서버가 따로 있음" → 실제: 같은 프로그램, 같은 프로세스, 같은 포트. 파싱 뒤 갈림길에서 나뉨. 따로 켜야 하는 건 백엔드뿐.
- **헷갈렸던 점 4:** 내 이해 "프록시를 통해서 accept됨" → 실제: accept는 프록시보다 훨씬 앞 단계이고 연결만 받음. 경로는 요청을 읽은 뒤에야 알 수 있음.
  - 손님 → 8080: **accept**(받는 쪽)
  - 8080 → 백엔드: **connect**(거는 쪽)
- **헷갈렸던 점 5:** 내 이해 "포워드는 accept 전에 추가됨" → 실제: 리버스와 같은 갈림길(파싱 뒤)에 가지가 하나 더 생김.
- **비유:** 식당. 웹서버 = 주방 음식 직접 내줌. 프록시 = 옆 가게(백엔드) 메뉴를 받아와 내줌. 메뉴판(`-P`)에 안 적으면 우리 주방만 씀.

### 백엔드로 요청 전달 (= 리버스 프록시 핵심 동작)
1. 백엔드에 `socket()` → `connect()`. 서버가 클라이언트 역할을 함.
2. 요청을 다시 씀: hop-by-hop 헤더 제거, `X-Forwarded-For` 추가, Host 유지.
3. 응답 받음.
4. 클라이언트에 그대로 돌려줌.
5. 실패 처리: 연결 거부 → 502, 시간 초과 → 504.
- **동적 처리인 이유:** 요청마다 앱 로직이 응답을 만듦. README의 "백엔드로 요청 전달"이 동적 처리 예시임.
- 응답도 **항상 프록시를 거침**. TCP 연결이 2개(손님↔프록시, 프록시↔백엔드)라서 백엔드는 손님에게 직접 보낼 길이 없음.
  - 예외: DSR(L4 LB 특수 구성). 우리와 무관.

### 프록시 비용 (느려지나?)
- hop마다 비용이 붙음: 연결 수립(TCP handshake), 데이터 복사 2번, 헤더 재파싱, fd 2배.
- 같은 데이터센터면 보통 1ms 미만. 진짜 시간은 DB·인터넷 왕복에 씀.
- 줄이는 법:
  - 백엔드 keep-alive 연결 풀 (효과 최대)
  - 스트리밍 중계
  - 캐싱 (오히려 빨라짐)
  - 정적 파일은 직접 `sendfile`
  - 이벤트 기반 I/O
- 측정값(WSL, c=50, keep-alive): 직접 약 8.5k req/s, 프록시 경유 약 5.3k req/s, 실패 0. 차이의 주원인은 요청마다 백엔드에 새로 connect하는 것.

### 프론트(엣지) 프록시 / 프록시 종류
- 프론트 프록시 = 서비스 맨 앞, 인터넷과 만나는 경계의 리버스 프록시(Envoy 용어).
- 하는 일: TLS 종료, 라우팅, 로드밸런싱, 공통 정책(인증, rate limit, 로깅).
- 사이드카 = 서비스 바로 옆 프록시(Istio).
  - 프론트 = north-south 트래픽(외부 → 내부)
  - 사이드카 = east-west 트래픽(서비스 ↔ 서비스)
- 과제 범위에서는 프론트 프록시 = 우리가 만든 리버스 프록시.

### 라우터
- 이 과제의 라우터 = 요청(경로, Host)을 보고 처리할 곳을 정하는 **소프트웨어 코드**(L7).
- 네트워크 라우터 = IP 주소(L3)를 보고 패킷을 넘기는 장비. 그 안도 결국 펌웨어·OS가 경로를 정함. 리눅스도 `ip_forward=1`이면 라우터가 됨.
- 공통점: 목적지를 보고 갈 곳을 정함. 보는 층만 다름.
- 대화 당시 `match_route()`는 설명용 예시 이름이었음. 실제 구현은 `rproxy_match`. 가장 긴 prefix가 이김(nginx 방식).

### 라운드로빈 / 로드밸런싱
- 라운드로빈 = 차례대로 하나씩 돌림(A→B→C→A). 구현: `atomic_fetch_add(&rr,1) % n`. 워커가 여러 개라 atomic 필요.
- 장점: 단순, 빠름. 단점: 서버 상태(바쁨, 성능, 죽음)를 안 봄 → failover나 헬스체크 필요.
- 다른 방식:
  - Weighted RR: 가중치만큼 더 보냄
  - Least Connections: 처리 중인 요청이 제일 적은 곳
  - IP Hash: 같은 손님은 같은 서버(세션 유지)
  - Random
- 로드밸런싱 = 요청을 여러 서버에 나눔. 리버스 프록시가 전달을 여러 서버에 나눠 하면 로드밸런서.
- **우리 서버:**
  - 있음: RR + failover(connect 실패 시 다음 백엔드)
  - 없음: 헬스체크, 가중치, least-conn, sticky session, 연결 풀
- **microhttp 여러 개 + LB:** `./microhttp -P /=127.0.0.1:8001,...:8002,...:8003 8080`으로 가능.
  - 장점: 장애 대비, 무중단 배포 흉내, 수평 확장 연습
  - 단점: 같은 컴퓨터면 오히려 느림(코어 수 동일 + hop 추가). LB가 단일 장애점. 헬스체크 없음. 상태 공유 문제.
  - 성능이 목적이면 `-t`로 스레드를 늘리는 게 나음.
- **LB 이중화:**
  - DNS 라운드로빈
  - VIP + keepalived/VRRP (active-standby)
  - 클라우드 LB(AWS ELB)
  - L4 LB → L7 LB 계층 구조
  - 이건 인프라 영역. C 코드로 할 일 아님.

### RST / FIN / ECONNRESET
| | FIN | RST |
|---|---|---|
| 의미 | 보낼 건 다 보냈음 | 연결 폐기 |
| 상대 `recv` 결과 | `0` (EOF) | `-1`, `errno=ECONNRESET` ("Connection reset by peer") |
| 안 읽은 데이터 | 온전함 | 상대 쪽에서 버려질 수 있음 |
- RST가 나가는 때:
  - 아무도 listen하지 않는 포트로 접속(Connection refused)
  - **안 읽은 수신 데이터가 남은 채로 `close()`**
  - `SO_LINGER` 0초
- **왜 그런 규칙인가** (RFC 1122 4.2.2.13, RFC 2525): FIN으로는 "보낸 데이터가 처리되지 않았다"를 알릴 수 없음.
  - 예: `POST /pay`를 안 읽고 닫았는데 FIN이면, 손님은 정상 종료로 착각함.
  - close하면 더 읽을 주체가 없으니 연결이 무효라고 즉시 알림.
- curl에서는 `curl: (56) Recv failure: Connection reset by peer`로 보임.
- **헷갈렸던 점:** 내 이해 "클라가 서버가 아무 응답도 안 했다는 걸 조용히 앎" → 실제: 응답 0바이트는 맞지만, 클라는 조용히 아는 게 아니라 `ECONNRESET` **에러를 받음**.

### 버그 수정 3개 (커밋 cba20da)
1. **빈 연결이 워커를 붙잡음 (slowloris)**
   - 원인: accept 직후 바로 워커로 감 → `tcp_recv_request`가 첫 바이트를 최대 5초 블로킹 대기. idle poller는 keep-alive 두 번째 요청부터만 쓰였음.
   - 수정: `server_dispatch_new`. `recv(MSG_PEEK|MSG_DONTWAIT)`로 확인함.
     - 데이터 있음 → `tp_submit`
     - 없음 → `idle_park`
     - 상대가 닫음 → close
     - 둘 다 가득 → 503
   - 한계: 첫 바이트만 보내고 나머지를 질질 끄는 경우는 여전히 워커를 붙잡음.
2. **과부하 때 503 대신 RST**
   - 원인: `server_on_idle_ready`는 요청이 와 있는 소켓을 그냥 close했고, `reject_busy`는 503 send 직후 close했음 → RST.
   - 수정 `server_reject_busy`:
     1. `recv(MSG_DONTWAIT)`로 최대 64KB 비우기 (`EAGAIN` → 멈춤, 0 → eof, `EINTR` → 재시도)
     2. `eof && total==0`(아무것도 안 보내고 닫은 상대: preconnect, 포트 스캐너, 쉬던 연결 종료)이면 503 생략
     3. 그 외는 `send(503, MSG_DONTWAIT|MSG_NOSIGNAL)` 후 close → FIN
   - 반대 경우 `eof && total>0` = half-close(요청 보내고 송신만 닫음) → 503 보냄.
   - 안 기다리는 이유: accept 스레드와 poller 스레드가 부르는 함수라 막히면 서버 전체가 멈춤.
   - 한계: close 뒤에 도착한 바이트는 여전히 RST.
3. **Ctrl+C 무시 (시그널 경쟁)**
   - 원인: `while(g_running)` 검사와 블로킹 `accept()` 사이에 시그널이 오면 EINTR 기회가 없음.
   - 수정: self-pipe.
     - 핸들러가 pipe에 1바이트 write(async-signal-safe)
     - 메인은 `poll([listen fd, pipe])`
     - listen fd는 O_NONBLOCK
     - 한 번에 최대 64개 accept
     - `ECONNABORTED`는 바로 다음으로
- 검증: 수정 전으로 되돌린 복사본에서 새 테스트가 실패하는 것을 확인함(변이 테스트). 3번은 타이밍 문제라 결정적인 테스트를 못 만듦.

### 503 / send 플래그
- **503 Service Unavailable** = 서버 멀쩡함, 지금 바쁨, 재시도 가능(5xx = 서버 쪽 사정).
  - 이 서버에서 보내는 때: 큐 가득(`QUEUE_CAP` 1024), poller 가득(`IDLE_MAX_CONNS` 10000), 종료 중.
  - 바이트: `HTTP/1.1 503 Service Unavailable\r\nContent-Length: 0\r\nConnection: close\r\n\r\n`
  - RST보다 나은 이유: 손님이 "바쁨"이라는 이유를 앎. RST는 네트워크 장애와 구분이 안 됨.
- **`MSG_DONTWAIT` = 안 막힘:** 송신 버퍼가 가득이면 잠들지 않고 바로 `-1 EAGAIN`.
- **`MSG_NOSIGNAL` = SIGPIPE 없음:** 끊긴 소켓에 send해도 프로세스가 죽지 않고 `-1 EPIPE`만 돌려줌.
  - main.c에서 SIGPIPE를 이미 무시 중이라 이중 안전장치.
  - macOS에는 이 플래그가 없어서 0으로 정의함.

### X-Forwarded-For
- 문제: 백엔드가 보는 상대는 프록시 IP뿐 → 로그, IP 차단, 통계가 틀어짐.
- 해결: 프록시가 `X-Forwarded-For: <손님IP>` 붙임. 여러 프록시를 거치면 뒤에 덧붙임(맨 앞이 원래 손님).
- 짝꿍: `X-Forwarded-Proto: http`.
- 주의:
  - 손님이 위조할 수 있음 → 믿을 수 있는 건 내 프록시가 붙인 마지막 값뿐.
  - 표준은 `Forwarded: for=`(RFC 7239)지만 XFF를 더 많이 씀.
- 쓰는 곳은 답장 주소가 아니라 백엔드의 판단(로그인 잠금, 지역, 주문 기록, rate limit).
- **헷갈렸던 점:** 내 이해 "프록시가 저장을 안 해서 백엔드가 알아야 함" → 실제: 프록시도 로그를 남김. **IP를 쓰는 판단 로직이 백엔드에 있어서** 넘겨주는 것.

### pxy_build_request 결과 예시 (한 줄)
`GET /api/x HTTP/1.1\r\nHost: example.com\r\nUser-Agent: t\r\nX-Forwarded-For: 10.0.0.9\r\nX-Forwarded-Proto: http\r\nConnection: close\r\n\r\n`
- `Connection: close`: 응답 하나 주고 끊으라는 뜻 → 응답 끝이 분명해짐.
- 버리는 헤더:
  - hop-by-hop(`Connection`, `Keep-Alive`, `Upgrade`, `TE`, `Trailer`, `Proxy-Connection` + `Connection`에 적힌 이름)
  - `Expect`, `Transfer-Encoding` (본문은 프록시가 이미 받음)
  - 손님이 보낸 `X-Forwarded-Proto` (위조 방지)
  - (포워드 추가 후) `Proxy-Authorization`, 그리고 `replace_host`면 `Host`

### proxy_core 함수 (상세는 docs/proxy_core_함수정리.md)
- `pxy_build_request(out, cap, req, opts)`: 상대에게 보낼 요청 머리.
  - 포워드 추가 후 `pxy_req_opts{target, client_ip, host, replace_host}` 구조체로 바뀜.
- `pxy_parse_response_head(buf, head_len, info)`: 응답 머리 검사.
  - 상태 줄 `HTTP/1.x DDD`(100~599)
  - CR/LF/NUL, obs-fold, 서로 다른 CL → -1 → 502 (응답 분할 방지)
  - TE가 있으면 CL 무시
- `pxy_rewrite_response_head(out, cap, buf, head_len, keep_alive)`: `HTTP/1.1` + hop-by-hop 제거 + `Connection: keep-alive|close`.
- `pxy_exchange(bfd, cfd, req, opts, backend_to, client_to, *keep, *status)`: 보내기 → 1xx 건너뛰기(101 → 502) → 본문 모드 → 머리 + 앞부분 전송 → 16KB 중계. bfd는 이 함수가 닫음.
  - 본문 모드: NONE(HEAD/204/304) / LENGTH(keep 유지) / EOF(chunked·길이 없음 → keep=0)
  - 반환: 0 = 완료 / >0 = 아직 안 보냄, 호출자가 그 코드로 오류 응답 / -1 = 중간 실패, 연결 끊기
- 내부 static 도우미: `lower`, `ieq_n`, `ieq`, `list_has`, `is_hop_by_hop`, `sbuf`/`sb_put`/`sb_str`(넘치면 err만 켬), `req_conn_lists`, `line_end`, `split_header`, `resp_conn_lists`.

### 프록시와 스레드
- 프록시는 따로 도는 스레드가 아님. 일반 요청과 같은 워커 안에서 실행됨 → 최대 N개 동시(`-t`).
- 요청 하나 안에서는 블로킹(connect → send → recv). 느린 백엔드는 워커를 최대 `-T`만큼 묶음.
- 공유하는 건 atomic `rr` 카운터뿐. 라우트 표는 읽기 전용, 버퍼는 각 워커 스택.
- 개선 방향: nginx처럼 epoll로 백엔드 소켓까지 비동기 처리(구조가 크게 바뀜).

### 웹서버 / WAS / 정적 vs 동적
- 웹서버 = HTTP로 요청을 받아 응답하는 프로그램. microhttp 전체가 웹서버이고, 정적 파일은 그중 한 기능.
  - 연결 받기, 동시 처리, HTTP 해석, 라우팅, 정적 파일, 전달, 응답 생성, 보호(타임아웃, 503, 크기 제한)
- **정적:** 있는 파일을 그대로(누가 요청해도 같음). **동적:** 요청마다 계산(로그인, DB).
- 우리 웹서버가 직접 하는 일:
  - GET/HEAD → `www` 파일
  - POST → echo
  - 그 외 메서드 → 501 (프록시 경로 제외)
- **POST echo** (`send_echo`):
  - 본문을 Content-Length만큼 받음(최대 1MB, chunked는 501)
  - 요약(method/uri/version/host/headers/keep-alive/body-length) + 본문을 `writev` 세 조각으로 보냄
  - 경로 무관, 저장 없음, 디버그·데모용
  - `-P` 경로에 맞으면 POST라도 백엔드로 감
- 진짜 동적 처리 방법: 리버스 프록시로 앱 서버에 넘김(전형적인 nginx + 앱 서버). 그 밖에 CGI, 서버 안 C 핸들러.
- 비유: 웹서버 = 식당 홀, 앱 서버 = 주방.
- **WAS**(Web Application Server) = 코드를 실행해 응답을 만드는 서버(Tomcat, Gunicorn, Node).
  - 웹서버(Nginx)가 앞에서 정적을 처리하고, 동적은 WAS로 넘김(= 리버스 프록시).
- **옛날 vs 지금:**
  - 옛날 = 서버에 앱을 올림. Tomcat에 `.war`를 넣음. 푸드코트(건물 하나에 가게 여럿).
  - 지금 = 앱 안에 서버가 있음. Spring Boot 내장 Tomcat, Go `ListenAndServe`. 푸드트럭.
  - 핵심 차이: **포트를 누가 여나.** 실행 파일 하나 = 프로세스 하나 = 포트 하나 → Docker로 여러 개 띄우고 앞에 리버스 프록시.
  - microhttp는 `main()`에서 직접 socket/bind/listen → "지금" 방식.

### 3티어 / N티어
- 3티어:
  1. 프레젠테이션 = 웹서버 (nginx, 우리 서버)
  2. 애플리케이션 = 앱 서버 (Spring, Node)
  3. 데이터 = DB (MySQL)
- 나누는 이유: 층별로 따로 확장, 보안(DB 숨김), 유지보수.
- 우리 서버 = 1층. 테스트의 가짜 백엔드가 2층을 흉내 냄.
- 4티어: 표준 없음.
  - 브라우저를 한 층으로 세는 경우
  - 중간에 캐시·내부 API 층을 끼우는 경우
- 숫자보다 "역할별로 나눠 따로 늘리고 숨기기"가 핵심. 층이 늘면 hop도 늘어 느려짐.

### 소켓
- 소켓 = 네트워크 통신 끝점("전화기"). OS가 만들고 프로그램은 fd(정수)로 다룸.
- 서버 순서: `socket` → `bind`(포트) → `listen` → `accept`(손님 전용 소켓 생성) → `recv`/`send` → `close`.
- 클라이언트 순서: `socket` → `connect` → `send`/`recv` → `close`. 프록시가 백엔드에 붙을 때 이 역할(`tcp_connect`).
- 주소 = IP(어느 컴퓨터) + 포트(어느 프로그램).
- **헷갈렸던 점:** 내 이해 "정수 fd는 BSD 소켓일 때만" → 실제: BSD 소켓은 **API 모양**(4.2BSD, 1983)이고, 정수 fd는 **유닉스 설계**("모든 게 파일")임.
  - Windows Winsock은 BSD API를 흉내 내지만 `SOCKET` 핸들을 씀(파일 fd와 별개).
  - `WSAStartup`, `closesocket`, `WSAGetLastError`, `INVALID_SOCKET`.
  - 그래서 "번호표 소켓"은 POSIX 계열에서만 성립.
- WSA = Windows Sockets API(Winsock). WSL과 혼동 주의. 사용자가 원래 물은 건 WAS였음.

### 캐싱 프록시
- 현재 없음. 응답을 저장해 두고 재사용하는 것.
- 설계 포인트:
  - 키 = 메서드 + Host + URI (GET/HEAD만)
  - 저장 조건: 200 + Content-Length + `no-store`/`private` 아님 + 크기 제한
  - 만료: `max-age`/`Expires`
  - 락(워커 동시 접근), LRU
- 넣을 곳: `pxy_exchange`(공통 부품) 또는 `proxy_cache.c`.
- 주의: `Authorization`/`Cookie` 요청은 저장하지 않음. 데이터가 바뀌어도 만료 전까지는 옛 응답을 줌.
- Redis 불필요:
  - 프로세스 1개라 워커끼리 메모리 해시맵을 공유함
  - Redis는 네트워크 왕복이라 더 느림
  - POSIX 소켓만 써야 해서 클라이언트 라이브러리 사용 불가(RESP 직접 구현해야 함)
  - DB가 없음

## 사이드 채팅
### 사이드 1: 라우터가 뭐야
1. Q: 라우터가 뭐야 → A: 요청을 보고 처리할 곳을 정하는 코드(L7). 네트워크 라우터(L3, IP)와 비교.
2. Q: 하드웨어 아냐? → A: 둘 다. 장비면 하드웨어 라우터, 코드면 소프트웨어 라우터.
3. Q: 아직 없어? match_route는? 과제 요구는? → A: 당시 없음. match_route는 예시 이름(가장 긴 prefix 매칭). 과제 필수 = 프록시 하나 이상 + 동적 처리.
4. Q: 백엔드로 요청 전달이 뭐야 → A: connect → 다시 쓰기 → 응답 받기 → 돌려주기 → 502/504. 이것이 동적 처리.
5. Q: 백엔드 요청 = 리버스 프록시? → A: 거의 같은 말(답변 도중 중단).
6. Q: 프록시 많아지면 느려지나 → A: hop 비용 있지만 작음. 연결 풀, 스트리밍, 캐시로 줄임. 이득(LB, 보안, 장애 격리)이 더 큼.
7. Q: 프론트 프록시 → A: 엣지에 둔 리버스 프록시. 프록시 종류 표(포워드, 리버스, 프론트, 사이드카).
8. Q: 아 포워드 프록시 → A: 클라이언트 대리인. absolute-form, getaddrinfo, CONNECT. 과제 기준 비교.
9. Q: 라운드로빈이란 → A: 차례대로 돌림. atomic 카운터, 장단점, 다른 방식들.

### 사이드 2: RST가 뭐야
1. Q: RST가 뭐야 → A: TCP 강제 종료 플래그. FIN과 비교표, 나가는 경우, 이번 버그 흐름.

### 사이드 3: server_on_idle_ready / reject_busy 문장 뜻
1. Q: 이 문장 무슨 뜻? → A: 두 경로 모두 요청을 읽지 않은 채 close → RST. 수정 순서는 비우기 → 503 → close.
2. Q: ECONNRESET이 뭐야 → A: RST를 받았다는 errno. FIN(0)과 비교(답변 도중 중단).
3. Q: 클라가 서버 무응답을 봤다는 거지? → A: 응답 0바이트는 맞음(도중 중단).
4. Q: 이어서 → A: 조용히 아는 게 아니라 `recv -1 ECONNRESET` 에러. curl은 (56).
5. Q: 왜 수신 버퍼가 남아 있으면 RST를 보내? → A: RFC 1122 규정. FIN으로는 "처리 안 됨"을 전할 수 없음(POST /pay 예). 읽을 주체가 사라짐.

### 사이드 4: server_reject_busy 구현 (caveman)
1. Q: 어떻게 구현돼서 고쳤어? → A: 비우기(64KB, DONTWAIT) → 503 여부 결정 → close로 FIN. 안 기다리는 이유, 한계, 변이 테스트.
2. Q: `eof && total==0`이 뭐야 → A: 연결만 하고 0바이트로 닫은 상대(preconnect, 스캐너, 쉬던 연결 종료) → 503 생략. half-close는 503 보냄.
3. Q: 503이 뭐지 → A: Service Unavailable. 이 서버에서 보내는 3가지 경우, 실제 바이트, 다른 코드와 비교, RST보다 나은 이유.
4. Q: "안 막힘, SIGPIPE 없음" 뜻 → A: `MSG_DONTWAIT`, `MSG_NOSIGNAL` 설명.

5. Q: 여러 서버로 나눠 보내는 게 뭐였더라 → A: 로드밸런싱. RR, failover, 다른 방식 표.
6. Q: 현재 구조 그림으로 → A: 위젯 다이어그램(초록 = microhttp 내부, 주황 = 프록시 경로·백엔드).
7. Q: 포워드 추가하면 accept 전에? → A: 아님. 같은 갈림길에 http://, CONNECT 가지 추가. `-F`로 오픈 프록시 방지.
8. Q: 웹서버는 정적만 처리? → A: 거의. GET/HEAD 정적, POST echo, 나머지 501. 진짜 동적은 앱 서버(리버스 프록시), CGI, 핸들러.
9. Q: 현재 POST 작동은? → A: `send_echo` 흐름, 예시 응답, 특징.
10. Q: 나중에 POST도 백엔드로? → A: 지금도 됨. `-P` 경로면 메서드 무관. 선택지 표.
11. Q: 그럼 웹서버 역할은? → A: HTTP 통신 담당 전체(역할 표). 직접 할 수 있는 건 직접, 못 하는 건 앱 서버에 넘김. 홀/주방 비유.

### 사이드 12: WSA → WAS
1. Q: WSA가 뭐야 → A: Winsock(Windows Sockets API) / Windows Subsystem for Android. WSL과 혼동 주의.
2. Q: WAS다 → A: Web Application Server. 웹서버 vs WAS 표, 함께 쓰는 구성.
3. Q: 옛: 서버에 앱 / 지금: 앱 안에 서버 / 실행 파일 하나 = 서버 하나 뜻? → A: Tomcat + war vs Spring Boot jar. 배포 단위, Docker.
4. Q: 차이를 잘 모르겠어 → A: 푸드코트 vs 푸드트럭. 코드 비교(Servlet vs Go main). 핵심은 포트를 누가 여나.

### 사이드 13: 3티어
1. Q: 3티어가 뭐야 → A: 프레젠테이션 / 애플리케이션 / 데이터. 흐름, 나누는 이유, 우리 서버는 1층.
2. Q: 4티어도 있나 → A: 표준 없음(N티어). 브라우저를 셈 / 캐시층 추가. 숫자보다 역할 분리가 핵심.

### 사이드 14: 로드 밸런서
1. Q: 로드 밸런서 없지? → A: 단순한 것 있음(RR + failover). 헬스체크, 가중치 등은 없음.
2. Q: 내 웹서버 여러 개 열고 LB 적용 가능? → A: 가능. `-P /=8001,8002,8003`(답변 도중 중단).
3. Q: 장단점 → A: 장애 대비, 확장 연습 / 같은 컴퓨터면 느림, LB 단일 장애점, 헬스체크 없음.
4. Q: 로드 밸런서도 여러 개? → A: DNS RR, VIP + VRRP, 클라우드 LB, L4 → L7 계층. 인프라 영역.

## 남은 일 / 더 볼 것
- 백엔드 keep-alive 연결 풀 (프록시 처리량 차이의 주원인).
- 캐싱 프록시(`proxy_cache.c`, 메모리 해시맵 + LRU). Redis는 불필요.
- chunked 응답 경계 해석 → chunked 뒤에도 클라이언트 keep-alive 유지.
- 터널과 느린 백엔드가 워커를 점유함 → epoll 기반 비동기 프록시 검토.
- `getaddrinfo` 타임아웃 없음, IPv4 전용, `GET https://` 미지원, 101 Upgrade(WebSocket) 미지원.
- 헤더를 질질 끄는 slowloris → 헤더 수신까지 이벤트 루프로 옮기기.
- 성능 nit 4건: 종료 지연(`tp_wake_fd`), `tp_queued` atomic, 로깅 병목, poller entry 풀.
- 403(비 loopback 클라이언트)은 기능 테스트 없음, 실제 curl + 외부 사이트로 포워드 미확인.
- docs 파일 2개 미커밋(`5.-동시성-구현.md`의 `tp_sbumit` 오타 확인 필요, `proxy_core_함수정리.md`는 `pxy_req_opts` 변경 전 인자 기준).
- 헬스체크, 가중치 등 LB 고급 기능은 선택.
