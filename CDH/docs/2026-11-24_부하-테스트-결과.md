# 부하 테스트 결과 — 4단계 (정적 파일, 반복형 서버)

측정: 2026-11-24, WSL2 Ubuntu (커널 6.6, 24 CPU), loopback, 각 조합 3초.
서버: `make` 기본 빌드(-O2), `-q`, Linux sendfile 경로. 요청마다 연결 1개 (서버가 `Connection: close`).

## 재현
```sh
make bench                                   # 기본: /index.html, 1MB, 10MB × 동시 1/10/50/100
DUR=10 CONCS="1 10 100" PATHS="/1m.bin" make bench
```
- 부하 생성기: `tests/bench.c` (스레드 c개가 d초 동안 "연결 → GET → EOF까지 수신" 반복, wrk/hey 방식)
  - 상태 200과 `Content-Length` = 받은 본문 길이까지 확인 → 어긋나면 fail
- `ab` / `wrk` / `hey`가 깔려 있으면 `tests/bench.sh`가 같은 서버에 비교용으로 한 번씩 더 돌림
  - 이번 환경엔 없음 (`sudo apt install apache2-utils wrk`)

## 해석
- 모든 조합에서 실패 0개. 1MB/10MB 본문도 바이트 수까지 일치.
- **처리량은 동시 10에서 최대, 그 뒤로는 평평하거나 떨어짐.** 서버가 한 번에 연결 하나만 처리(반복형)하기 때문.
  - 동시 1 → 10에서 오르는 이유: 클라이언트가 connect·수신하는 시간과 서버 처리 시간이 겹침 (서버가 놀지 않음).
- **지연 시간은 동시 연결 수에 거의 비례해서 늘어남.** 대기열(listen backlog)에서 차례를 기다리는 시간.
  - 10MB: p50이 1ms(동시 1)에서 125ms(동시 100)로 늘어남. 앞의 99개가 끝날 때까지 기다리기 때문.
- 큰 파일은 sendfile 덕분에 연결 하나로도 약 9.5GB/s (loopback 기준. 실제 네트워크에선 회선 속도가 한계).
- 동시 100 + 10MB에서 처리량이 떨어짐(1,216 → 843 req/s). 클라이언트 스레드 100개가 CPU·캐시를 두고 경쟁하는 영향으로 보임.
- → 5단계(동시성)에서 같은 표를 다시 재서 비교: 동시 50/100의 req/s와 p99가 개선 목표.
