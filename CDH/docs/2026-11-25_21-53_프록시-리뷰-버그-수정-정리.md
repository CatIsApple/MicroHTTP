## 1. `-F any` SSRF (내부망 접근)

### 왜 발생했나
- 수정 전 `connect_target`(지금 [fproxy.c:281](../src/fproxy.c:281))은 클라이언트가 적은 host:port로 그대로 connect함.
- 검사는 **클라이언트 IP**(`fproxy_client_allowed`, [fproxy.c:144](../src/fproxy.c:144))만 하고, **목적지**는 안 봄.
- `-F local`이면 클라이언트가 이미 로컬 사용자라 문제없음. `-F any`면 인터넷의 누구나 서버를 디딤돌로 써서 서버 내부로 들어올 수 있음.

```
공격자 ──CONNECT 127.0.0.1:6379──> 우리 프록시 ──> 루프백 전용 Redis
공격자 ──GET http://169.254.169.254/──> 우리 프록시 ──> 클라우드 메타데이터(키 유출)
```
- CONNECT는 포트 제한도 없었음 → SMTP(25) 중계 같은 스팸 경유지로도 쓰일 수 있었음.

### 어떻게 고쳤나
- 새 함수 `fproxy_dest_allowed` ([fproxy.c:152](../src/fproxy.c:152)) 추가.
  - `-F local`: 항상 허용 (기존 동작 유지).
  - `-F any`: 아래 대역은 403으로 거절.

| 대역 | 이유 |
|---|---|
| `0.0.0.0/8` | "이 호스트" (`http://0/` = 내 컴퓨터) |
| `10/8`, `172.16/12`, `192.168/16` | 사설망 |
| `100.64/10` | CGNAT |
| `127/8` | 루프백 |
| `169.254/16` | 링크 로컬 (클라우드 메타데이터) |
| `224/4` 이상 | 멀티캐스트·예약 |

  - CONNECT는 **443 포트만** 허용.
- 검사 위치는 **이름 해석 뒤** ([fproxy.c:289](../src/fproxy.c:289) 부근, `connect_target` 안). `http://localhost/`나 내부 IP를 가리키는 도메인처럼 이름으로 우회해도 막힘.
- 결과는 `-403` → [server.c](../src/server.c)가 403으로 응답.

### 테스트
- [test_fproxy.c:119](../tests/test_fproxy.c:119) `test_dest_allowed`
  - 차단 12개, 허용 8개 (경계값 `100.63.255.255`, `172.32.0.1` 등)
  - 포트 검사(443 허용, 25 거절)
- [test_functional.c:1200](../tests/test_functional.c:1200) 부근 `-F any` 서버로 확인: `127.0.0.1`, CONNECT 루프백, `localhost:6379`, `169.254.169.254` 모두 403.

## 2. CONNECT 터널이 워커를 하나씩 점유

### 왜 발생했나
- 터널 중계 루프 `while (open[0] || open[1])` ([fproxy.c:358](../src/fproxy.c:358))는 **워커 스레드 안에서** 돎.
- 터널은 양쪽이 60초(`FPROXY_TUNNEL_IDLE_MS`) 동안 완전히 조용해야 닫힘. 브라우저의 HTTPS 연결은 오래 열려 있음.
- 그래서 터널 수가 워커 수(`-t`)에 닿으면 남는 워커가 없음.
  - 정적 파일 요청도 큐에서 대기함.
  - 새 연결은 503을 받음.

```
워커 16개 = 터널 16개 → GET /index.html 처리할 워커 0개
```

### 어떻게 고쳤나
- 동시 터널 수에 상한을 둠.
  - `fproxy_config`에 `max_tunnels`, `atomic_int tunnels` 추가 ([fproxy.h](../include/fproxy.h)).
  - `fproxy_tunnel` ([fproxy.c:319](../src/fproxy.c:319))은 시작할 때 `atomic_fetch_add`하고, 상한을 넘으면 바로 되돌리고 503 ([fproxy.c:326](../src/fproxy.c:326)).
  - 실제 중계는 `tunnel_run` ([fproxy.c:335](../src/fproxy.c:335))으로 분리함. 어떤 경로로 끝나든 카운터가 반드시 1 줄도록 하려고.
  - 상한 = 워커 수의 절반 (최소 1). [main.c:205](../src/main.c:205)에서 `-t` 값으로 정함.
- 카운터를 바꿔야 해서 `server_ctx.fproxy`를 `const`가 아닌 포인터로 바꿈 ([server.h](../include/server.h)).
- 근본 해결(터널을 epoll 이벤트 루프로 옮기기)은 구조 변경이 커서 이번엔 상한만 둠.

### 테스트
- [test_functional.c:1175](../tests/test_functional.c:1175) 부근, 워커 2개 서버(→ 터널 1개까지) 사용:
  1. 첫 CONNECT → `200 Connection Established`
  2. 두 번째 CONNECT → **503**
  3. 그동안 `GET /style.css` → 200 (일반 요청은 계속 처리됨)
  4. 첫 터널을 닫은 뒤에도 정상

## 3. `getaddrinfo` 시간 제한 없음

### 왜 발생했나
- 수정 전 `connect_target`은 워커 스레드에서 `getaddrinfo`를 바로 호출함.
- `getaddrinfo`는 마감 시간을 줄 수 없음. DNS가 느리면 시스템 resolver 설정(보통 5~30초)만큼 블로킹됨.
- `-T` 타임아웃은 이 구간을 감싸지 않았음.
- 결과: 해석이 느린 이름(`http://random.slow-dns.example/`)으로 워커 수만큼 요청하면 서버 전체가 멈춤.

### 어떻게 고쳤나
- 마감 시간이 있는 해석 함수 `resolve` ([fproxy.c:222](../src/fproxy.c:222)) 추가.
  1. **숫자 IP면 바로 사용** (`inet_pton`). DNS를 거치지 않음.
  2. 이름이면 **별도 detached 스레드** `dns_thread` ([fproxy.c:199](../src/fproxy.c:199))에서 `getaddrinfo` 실행.
  3. 워커는 `pthread_cond_timedwait`로 최대 `FPROXY_DNS_TIMEOUT_MS`(3초, `-T`가 더 짧으면 그 값)만 기다림. 넘으면 **504**.
  4. 진행 중인 해석이 `FPROXY_MAX_DNS`(32)개를 넘으면 **503**. 느린 DNS 때문에 스레드가 끝없이 늘지 않게 하려고.
- 메모리 수명: 작업 구조체 `dns_job`에 `refs = 2`(워커 + 해석 스레드)를 둠. 늦게 끝나는 쪽이 `dns_release`에서 free함. 그래서 워커가 먼저 포기하고 떠나도 안전함.

### 테스트
- 존재하지 않는 호스트(`no-such-host.invalid`) → 502. 새 해석 스레드 경로로 동작 확인.
- **3초 마감 자체는 느린 DNS를 재현할 수 없어서 테스트 없음.**

### 남은 한계
- 서버 종료 시점에 해석 스레드가 돌고 있으면 그 `dns_job`은 회수되지 않음. 이번 ASan 테스트에서 보고는 없었음.

## 4. 1바이트씩 흘리는 목적지 (slow origin)

### 왜 발생했나
- `pxy_exchange`의 본문 중계 루프는 `tcp_recv_some(bfd, ..., resp_to)`를 반복함 ([proxy_core.c:429](../src/proxy_core.c:429), [proxy_core.c:440](../src/proxy_core.c:440) 부근).
- `resp_to`(`-T`)는 **한 번 읽을 때마다 새로 시작**됨. 전체 마감은 없었음.
- 그래서 악성 서버가 `Content-Length: 1000000`을 보낸 뒤, 타임아웃 직전마다 1바이트씩 보내면 워커가 사실상 영원히 묶임.
- 리버스 백엔드는 운영자가 정한 믿는 서버지만, 포워드 목적지는 **인터넷의 아무 서버**라 이게 실제 위험이 됨.
- 같은 원리의 구멍 하나 더: 1xx 응답만 계속 보내면 응답 머리 루프가 끝나지 않았음.

### 어떻게 고쳤나
- `pxy_req_opts`에 최저 속도 필드 추가 ([proxy_core.h](../include/proxy_core.h)): `min_rate_bps`, `rate_grace_ms`. 0이면 끔.
- `rate_wait` ([proxy_core.c:320](../src/proxy_core.c:320)) 추가. 다음 recv를 얼마나 기다릴지 계산함:
  ```
  허용 시간 = rate_grace_ms + (받은 바이트 × 1000 / min_rate_bps)
  남은 시간 = 본문 시작 시각 + 허용 시간 − 지금
  남은 시간 ≤ 0 → 중단(-1),  아니면 min(남은 시간, resp_to)
  ```
  - 기준 시각은 본문 시작 ([proxy_core.c:426](../src/proxy_core.c:426)). 응답 머리를 기다린 시간은 넣지 않음.
- 포워드만 켬 ([fproxy.c:311](../src/fproxy.c:311)): 1KB/s(`FPROXY_MIN_RATE_BPS`), 처음 `-T` 동안은 봐줌. 리버스는 0(끔). 정상적으로 느린 큰 다운로드도 평균 1KB/s만 넘으면 끊기지 않음.
- 1xx 상한 `PXY_MAX_1XX` = 8 ([proxy_core.c:26](../src/proxy_core.c:26), 검사는 [proxy_core.c:360](../src/proxy_core.c:360)). 넘으면 502.

### 테스트
- 가짜 백엔드에 두 경로 추가 ([test_functional.c:252](../tests/test_functional.c:252), [test_functional.c:260](../tests/test_functional.c:260)):
  - `/api/trickle`: 100ms마다 1바이트 (끝까지 가면 10초)
  - `/api/many1xx`: `100 Continue` 20개 뒤에 200
- 포워드로 요청해서 확인 ([test_functional.c:1103](../tests/test_functional.c:1103) 부근):
  - trickle → 2초 안에 잘린 채로 끊김
  - many1xx → 502

## 5. 죽은 백엔드에 매번 connect

### 왜 발생했나
- `rproxy_handle`은 라운드 로빈 순서대로 `tcp_connect`하고, 실패하면 다음 백엔드로 넘어감 (failover).
- 하지만 **실패를 기억하지 않음**. 그래서 다음 요청도 죽은 백엔드에 다시 connect부터 시도함.
- 백엔드가 RST 없이 패킷을 버리는 상태(방화벽, 꺼진 호스트)면 connect가 `PXY_CONNECT_TIMEOUT_MS`(2초)까지 걸림.
  - `A, B` 중 A가 죽음 → 절반의 요청이 2초씩 늦어짐.
  - 부하가 걸리면 워커가 전부 `tcp_connect`에서 대기함.

### 어떻게 고쳤나
- 백엔드마다 `atomic_llong down_until` 추가 ([rproxy.h](../include/rproxy.h)). 초기화는 [rproxy.c:134](../src/rproxy.c:134).
- `rproxy_handle` ([rproxy.c:210](../src/rproxy.c:210)~[rproxy.c:225](../src/rproxy.c:225)):
  - connect 실패 → `down_until = 지금 + RPROXY_DOWN_MS`(5초). 그동안 건너뜀.
  - connect 성공 → `down_until = 0` (되살아남).
  - **전부 죽음 표시면 표시를 무시하고 모두 시도**함. 되살아났는지 확인하려고(수동적 헬스 체크).
  - 504/502 판정은 "실제로 시도한 백엔드" 기준으로 바꿈.
- 시각은 `CLOCK_MONOTONIC`(`mono_ms`, [rproxy.c:22](../src/rproxy.c:22))을 씀. 시스템 시각이 바뀌어도 거꾸로 가지 않음.
- 여러 워커가 동시에 읽고 쓰므로 atomic 사용 (TSan 통과).

### 테스트
- [test_rproxy.c:271](../tests/test_rproxy.c:271) `test_down_marking` (닫힌 포트 두 개 사용):
  1. 둘 다 실패 → 502, 둘 다 표시됨
  2. 다시 요청 → 전부 죽음이라 다시 시도함 (표시 갱신)
  3. 하나만 죽음 표시 → 그 백엔드는 건너뜀 (표시 값이 그대로)
