# 7. 구현 질문 세례 — 세션 정리 (2026-11-26 10:13)
세션 ID: f62f0d70-49fd-4fc2-a04a-65f30b553353 · 사이드 채팅은 요청에 따라 제외함 (8개 있음)

## TL;DR
- 현재 TCP 서버 구조: `tcp_server.c`는 바이트만 다루는 소켓 계층, `main.c`가 poll + accept 루프를 돌리고 스레드 풀과 idle poller로 연결을 넘김.
- 모든 송수신은 논블로킹 + poll이고, 호출 전체에 마감 시간을 걺 → slowloris 방어.
- 송신 경로: `sendmsg`+iovec, 파일은 `sendfile` zero-copy. 종료는 `tcp_close_graceful`로 RST 없이 닫음.
- 같은 서버를 다르게 만드는 방법 52가지를 영역별로 정리함 (동시성, accept, I/O, 파싱, 프로토콜, 프록시, 라이브러리, 언어, 구조).
- 다음 학습 추천: epoll reactor + 연결별 상태 머신.

## 핵심 개념 정리

### 현재 TCP 서버 구현
- 계층 분리: `src/tcp_server.c`는 HTTP를 모름. `main.c`가 연결 루프, `server.c`가 HTTP 처리.
- `tcp_listen` (`tcp_server.c:40`): `socket(AF_INET, SOCK_STREAM)` → `SO_REUSEADDR` (TIME_WAIT 포트도 재바인딩 가능) → `bind(0.0.0.0:port)` → `listen(backlog)`.
  - 그다음 main이 리스닝 fd를 `O_NONBLOCK`으로 바꿈 (`main.c:224`). 이유: poll이 "연결 있음"이라고 한 뒤 accept 전에 상대가 RST로 사라지면 블로킹 accept는 다음 연결까지 잠듦.
- accept 루프 (`main.c:276`):
  - `poll`로 리스닝 fd와 시그널 self-pipe 2개를 감시.
  - 연결이 오면 `ACCEPT_BATCH`개까지 한 번에 accept. EAGAIN이면 다시 poll. ECONNABORTED는 건너뜀.
  - fd가 고갈되면 미리 잡아 둔 예비 fd(`/dev/null`)를 써서 `handle_accept_error`가 처리.
  - `server_dispatch_new`: 데이터가 이미 와 있으면 스레드 풀로, 아직 없으면 idle poller로 넘김 (fd 소유권도 같이 넘어감).
- `tcp_accept` (`tcp_server.c:80`):
  - 리눅스는 `accept4(SOCK_NONBLOCK|SOCK_CLOEXEC)`, 그 외는 accept 후 `fcntl`로 같은 플래그를 켬.
  - 논블로킹인 이유: 모든 I/O가 "시도해 보고 EAGAIN이면 poll" 방식이고, sendfile 때마다 fcntl을 껐다 켜는 시스템콜을 없애려고.
  - CLOEXEC인 이유: 나중에 fork+exec(CGI 등)를 할 때 자식에게 연결 소켓이 새지 않게.
- 마감 시간: `now_ms` (`CLOCK_MONOTONIC`) + `wait_until` (poll, EINTR이면 남은 시간을 다시 계산해서 대기).
  - `SO_RCVTIMEO`는 recv 한 번에만 걸림 → 1바이트씩 천천히 보내는 slowloris를 못 막음. 그래서 호출 전체에 마감을 걺.
- 수신:
  - `tcp_recv_request`: `\r\n\r\n`이 나올 때까지 모음.
    - keep-alive 파이프라이닝 잔여 바이트에 헤더 끝이 이미 있으면 시스템콜 없이 바로 반환.
    - 새로 받은 구간 + 앞 3바이트만 검사 (매번 처음부터 찾으면 O(n²)).
    - `strstr` 대신 `memcmp` 길이 기반 검색 (중간에 `\0`이 있어도 멈추지 않음).
    - 버퍼가 꽉 찼는데 헤더 끝이 없으면 header_len 0 → 호출자가 431.
  - `tcp_recv_exact`: 본문을 정확히 len바이트 받음. 다 받기 전에 상대가 닫으면 ECONNRESET.
  - `tcp_recv_some`: 프록시 중계용. 와 있는 만큼 받음.
- 송신:
  - `sendv_until`: 메모리 송신은 전부 이 함수 하나로 지남. `sendmsg` + iovec, `MSG_DONTWAIT|MSG_NOSIGNAL`. 먼저 보내 보고 EAGAIN일 때만 poll.
  - `tcp_sendfile_all`:
    - 리눅스: 헤더를 `MSG_MORE`로 맡겨 두고 `sendfile` (zero-copy, 헤더와 본문이 한 패킷 → Nagle + delayed ACK 40ms 회피).
    - macOS: `sendfile`의 hdtr로 헤더까지 시스템콜 하나에.
    - 그 외: `pread` 64KB씩 + `sendmsg`.
    - 파일 송신 마감은 둘 중 이른 쪽: (1) 무진척 `timeout_ms`, (2) 최저 평균 속도 `TCP_SEND_MIN_RATE` = 16KiB/s. 전체 고정 마감이면 느린 회선에서 큰 파일을 영원히 못 받기 때문.
- `tcp_connect`: 프록시용. 논블로킹 connect → POLLOUT 대기 → `SO_ERROR`로 성공/실패 확인.
- `tcp_close_graceful` (`tcp_server.c:581`): 안 읽은 수신 데이터가 없으면 바로 close. 있으면 `shutdown(SHUT_WR)`로 FIN 먼저 → 최대 0.5초·64KB를 읽어서 버림 → close. 안 읽은 데이터를 남긴 채 close하면 커널이 RST를 보내 응답이 유실될 수 있음.
- 종료: 시그널 → self-pipe → 리스닝 close → `tp_shutdown` → `idle_stop` → `tp_destroy`.

### 다른 구현 방식 (각 1~3줄 설명)

#### 동시성 모델
1. **반복 서버**: 연결 하나를 끝까지 처리한 뒤 다음 연결 accept. 가장 단순하지만 느린 클라이언트 하나가 전체를 막음.
2. **fork-per-connection**: accept 후 `fork()`, 자식이 연결을 처리. 프로세스끼리 격리돼 안전하지만 fork 비용과 메모리가 큼.
3. **pre-fork**: 워커 프로세스 N개를 미리 띄워 두고 각자 같은 리스닝 fd에서 accept (Apache prefork). fork 비용이 없고 크래시가 격리됨.
4. **thread-per-connection**: 연결마다 `pthread_create`. 코드가 단순(블로킹 스타일)하지만 연결 수만큼 스레드 스택과 컨텍스트 스위치 비용이 듦.
5. **pre-thread / 스레드 풀** (현재 방식): 고정 N개 스레드 + 작업 큐. 스레드 생성 비용이 없고 동시성 상한이 생김. 느린 연결이 워커를 점유하는 게 약점이라 idle poller로 보완함.
6. **leader/follower**: 스레드 하나(leader)가 이벤트를 기다리다 오면 다른 스레드에 leader를 넘기고 자기가 처리. 큐 없이 컨텍스트 전달 비용이 줄어듦.
7. **select 이벤트 루프**: 단일 스레드가 `select`로 여러 fd를 감시. fd 수 제한(`FD_SETSIZE` 1024)이 있고 매번 O(n) 스캔.
8. **poll 이벤트 루프**: select와 같지만 fd 수 제한이 없음. 여전히 매번 전체 배열을 커널에 복사하고 O(n) 스캔.
9. **epoll/kqueue reactor**: 관심 fd를 커널에 한 번 등록하고 준비된 것만 받음 (O(준비된 수)). 논블로킹 + 연결별 상태 머신 필요 (nginx, redis).
10. **멀티 reactor + `SO_REUSEPORT`**: 코어마다 독립 이벤트 루프를 두고 커널이 연결을 분배. 락 없이 멀티코어를 활용함.
11. **main/sub reactor**: main 루프는 accept만, sub 루프들이 I/O를 맡음 (Netty, muduo). accept 부하와 I/O 부하가 분리됨.
12. **reactor + 워커 풀 하이브리드**: I/O는 이벤트 루프, 무거운 CPU 작업(압축, 동적 처리)만 풀에 넘김. 루프가 막히지 않게 함.
13. **proactor (io_uring / IOCP)**: "준비되면 알려줘" 대신 "이 I/O를 해 두고 끝나면 알려줘". 시스템콜 배치와 zero-copy로 최고 성능 노림.
14. **코루틴 / green thread**: 블로킹처럼 보이는 코드를 사용자 공간에서 전환 (ucontext, libco, Go goroutine). 이벤트 루프 성능에 코드는 순차적으로 쓸 수 있음.
15. **async/await 런타임**: 언어 차원의 코루틴 (Rust tokio, C++20 co_await). 컴파일러가 상태 머신을 자동 생성함.
16. **액터 모델**: 연결 하나 = 메시지만 주고받는 액터 하나 (Erlang/Elixir). 공유 메모리가 없고 장애가 격리됨.
17. **SEDA**: 파싱 → 처리 → 송신 단계마다 큐 + 스레드 풀. 단계별로 부하 조절(backpressure)이 가능함.
18. **shared-nothing (thread-per-core)**: 코어 하나에 스레드 하나를 고정하고 데이터 공유를 안 함 (seastar/ScyllaDB). 락과 캐시 경합이 없어짐.

#### accept 방식
19. **accept 스레드 하나 + 큐 분배** (현재 방식): 한 곳에서 받아 워커에 나눠 줌. 단순하지만 accept 스레드가 병목이 될 수 있음.
20. **다중 스레드가 같은 fd를 accept**: 각 워커가 직접 accept. 연결 하나에 모두 깨어나는 thundering herd 문제 → `EPOLLEXCLUSIVE`나 accept mutex로 완화.
21. **`SO_REUSEPORT`**: 스레드/프로세스마다 같은 포트로 리스닝 소켓을 따로 둠. 커널이 해시로 분배해서 경합이 없음.
22. **accept를 epoll 이벤트로**: 리스닝 fd도 이벤트 루프에 등록해 다른 I/O와 같이 처리. 별도 accept 스레드가 필요 없음.

#### I/O 방식
23. **블로킹 + `SO_RCVTIMEO`/`SO_SNDTIMEO`**: 소켓 타임아웃만 걸고 블로킹 recv/send. 코드는 단순하지만 타임아웃이 호출 한 번 단위라 slowloris에 약함.
24. **논블로킹 + poll 마감** (현재 방식): 시도 → EAGAIN → 남은 시간만큼 poll. 호출 전체 마감을 정확히 지킬 수 있음.
25. **`readv`/`writev`**: 여러 버퍼를 시스템콜 하나로 읽고 씀. 헤더와 본문을 복사 없이 한 번에 보냄 (`sendmsg`와 같은 효과).
26. **파일 송신 방식**
    - `sendfile`: 커널 안에서 페이지 캐시 → 소켓으로 바로 복사 (현재 방식).
    - `splice`/`tee`: 파이프를 거쳐 fd끼리 zero-copy. 소켓 → 소켓 프록시 중계에도 쓸 수 있음.
    - `mmap` + write: 파일을 메모리에 매핑해서 전송. 복사 1회가 줄지만 파일이 잘리면 SIGBUS 위험.
    - read + write: 사용자 버퍼로 복사. 가장 이식성이 좋고 가장 느림.
27. **소켓 옵션**
    - `MSG_ZEROCOPY`: 큰 버퍼 송신 시 커널 복사를 생략하고 완료 알림을 받음.
    - `TCP_CORK`: 코르크를 뽑을 때까지 패킷을 모음 (`MSG_MORE`를 소켓 단위로 하는 것).
    - `TCP_NODELAY`: Nagle을 끄고 작은 패킷을 바로 보냄.
28. **edge-triggered vs level-triggered**: LT는 데이터가 남아 있는 한 계속 알림. ET는 상태가 바뀔 때 한 번만 알리므로 EAGAIN이 날 때까지 다 읽어야 함 (시스템콜이 적어짐).
29. **타이머 구조**: timerfd(커널 타이머를 fd로), 타이머 휠(O(1) 등록·만료), 최소 힙(가장 이른 마감을 O(log n)으로 꺼냄). 연결이 수만 개일 때 타임아웃 관리용.
30. **signalfd / eventfd**: 시그널이나 스레드 간 알림을 fd 이벤트로 받음. self-pipe(fd 2개)를 fd 1개로 대체.

#### 파싱
31. **직접 스캔**: `\r\n\r\n`까지 모은 뒤 문자열 함수로 한 번에 파싱. 단순하지만 헤더 전체를 버퍼에 들고 있어야 함.
32. **증분 상태 머신 파서**: 바이트가 도착하는 대로 상태를 진행 (llhttp, http-parser). 버퍼를 다시 스캔하지 않고 이벤트 루프와 잘 맞음.
33. **파서 생성기**: ragel/re2c로 문법 정의 → 상태 머신 C 코드 자동 생성 (mongrel). 정확하고 빠름.
34. **SIMD 스캔**: SSE4.2/AVX2로 16~32바이트씩 구분자를 찾음 (picohttpparser). 헤더 파싱이 수 배 빨라짐.

#### 프로토콜 확장
35. **HTTP/1.x 기능 단계**: 1.0(요청마다 연결) → 1.1 keep-alive + 파이프라이닝 → chunked 전송(길이를 모르는 본문 스트리밍).
36. **HTTP/2**: 바이너리 프레임, 연결 하나에 스트림 여러 개를 멀티플렉싱, HPACK 헤더 압축 (nghttp2).
37. **HTTP/3 / QUIC**: UDP 위에서 TLS 1.3 + 스트림. HOL blocking과 연결 수립 RTT가 줄어듦 (quiche, ngtcp2).
38. **TLS**: OpenSSL/mbedTLS로 HTTPS. kTLS는 암호화를 커널로 내려서 sendfile zero-copy를 유지함.
39. **동적 처리**: CGI(요청마다 프로세스 fork+exec), FastCGI(상주 프로세스와 소켓 통신), `dlopen` 플러그인 모듈.

#### 프록시
40. **중계 방식**: recv → 버퍼 → send 단순 중계 vs `splice`로 소켓 → 파이프 → 소켓 zero-copy 양방향 중계.
41. **백엔드 커넥션 풀**: 백엔드 연결을 keep-alive로 재사용. 요청마다 3-way handshake를 하지 않아도 됨.
42. **로드밸런싱**: 라운드로빈 / least-connections / 해시(세션 고정) / 주기적 헬스체크로 죽은 백엔드 제외.
43. **CONNECT 터널**: 포워드 프록시에서 HTTPS를 지원하는 방법. 연결만 이어 주고 바이트를 양방향으로 그대로 중계.

#### 라이브러리 사용
44. **libevent / libev / libuv**: epoll/kqueue/IOCP를 감싼 크로스플랫폼 이벤트 루프 (libuv = Node.js 기반). 이식성이 확보됨.
45. **Boost.Asio**: C++ 비동기 I/O. 콜백, 코루틴, future 스타일을 모두 지원함.
46. **커널 우회**: DPDK로 NIC를 사용자 공간에서 직접 제어 + mTCP/F-Stack 같은 사용자 공간 TCP 스택. 초저지연, 초고처리량용.
47. **커널 안 서버**: 커널 모듈로 HTTP 처리 (khttpd, TUX). eBPF/XDP는 패킷 필터링·리다이렉트 정도만 가능.

#### 언어 / 플랫폼
48. **Windows Winsock + IOCP**: 완료 포트 기반 proactor. `TransmitFile`이 sendfile에 해당함.
49. **다른 언어**
    - Go: goroutine + netpoller로 블로킹 스타일인데 epoll 성능.
    - Rust: tokio/mio 비동기, 메모리 안전.
    - Java: NIO/Netty reactor.
    - Node: 단일 스레드 libuv 루프.
    - Python: asyncio.
    - Erlang/Elixir: 액터 + 경량 프로세스.

#### 구조
50. **모듈 분리 vs 단일 파일**: 계층별 파일(현재: tcp/parser/response/static/proxy) vs 단일 파일 서버. 테스트하기 쉬운 쪽과 읽기 쉬운 쪽의 트레이드오프.
51. **미들웨어 체인**: 요청 → [로깅 → 인증 → 압축 → 라우팅] 핸들러를 차례로 연결. 기능을 꽂았다 뺐다 할 수 있음 (Express, nginx 모듈 phase).
52. **마스터 + 워커 프로세스**: 마스터는 설정과 감시만, 워커가 처리 (nginx). 워커가 죽어도 재생성하고 무중단 재시작/설정 리로드 가능.

2. 요청: caveman 모드 최대로 유지 → 이후 답변을 caveman 스타일로 함.
3. Q: 이 프로젝트를 다른 방식으로 구현하는 방법은 뭐가 있나? 최대한 많이. → A: 영역별로 52가지 나열. 추천은 epoll reactor.
4. 요청: 세션 정리 (사이드 채팅 제외, 방식마다 1~3줄 설명 추가) → 이 문서.
