## 핵심 개념 정리

### `-F any` / 오픈 프록시
- `-F` 뒤 값 = 누구에게 포워드 프록시를 쓰게 할지.

| 옵션 | 허용 클라이언트 |
|---|---|
| `-F local` | `127.x`만. 나머지 403 |
| `-F any` | 전부 (인터넷 누구나) |
| `-F` 없음 | 포워드 꺼짐 |

- `any`를 쓰는 경우: 다른 PC나 폰의 Wi-Fi 프록시 설정에 `내PC IP:8080`을 넣을 때.
- 위험 = **오픈 프록시**. 아무나 내 서버를 경유지로 씀 → 스팸·공격이 내 IP에서 나간 걸로 찍힘.
- 기본은 `local`. `any`는 믿을 수 있는 망에서만.

### SSRF (서버를 내부망 침투 통로로 씀)
- 원인: `-F any`인데 **목적지 검사가 없었음**. 손님이 고른 곳으로 서버가 그대로 connect함.
```
공격자(외부) ──CONNECT 127.0.0.1:6379──> 우리 서버 ──> 서버 안 Redis
```
- Redis, DB, 관리자 페이지는 보통 "127.0.0.1에서만 허용"으로 막혀 있음.
- 그런데 우리 서버가 대신 connect하면 출발지가 127.0.0.1이 됨 → 내부 접속으로 보여 통과됨.
- 같은 방식으로 사내망(`10.x`, `192.168.x`)과 클라우드 메타데이터(`169.254.169.254`, 키 유출)까지 닿음.
- `-F local`이면 손님이 이미 서버 안에 있으니 피해 거의 없음.
- 수정:
  - **이름 해석 뒤** IP 대역 검사 → 403. 이름으로 우회(`localhost`, 내부 IP를 가리키는 도메인)해도 막힘.
  - CONNECT는 443만 허용 (SMTP 25 중계 같은 스팸 경유 차단).

### CONNECT 터널
- 정의: HTTPS용 바이트 통로.
  - HTTPS는 암호화돼 있어서 프록시가 요청을 읽거나 다시 쓸 수 없음.
  - 그래서 "저기까지 길만 뚫어 줘" 방식을 씀.
```
손님 → 프록시: CONNECT example.com:443 HTTP/1.1
프록시 → example.com:443 connect
프록시 → 손님: HTTP/1.1 200 Connection Established
이후: 손님 ⇄ 프록시 ⇄ example.com (암호 바이트 그대로 왕복)
```
- 비유:
  - `GET http://` 프록시 = **택배 기사**. 상자를 열어 보고 송장(헤더)도 고침.
  - CONNECT = **전화 교환원**. 선만 꽂아 주고 통화 내용은 안 들음(들어도 암호).

| | `GET http://a.com/x` | `CONNECT a.com:443` |
|---|---|---|
| 목적지 | 보임 | 보임 (host:port) |
| 경로 `/x` | 보임 | 안 보임 |
| 헤더·쿠키·본문 | 보임, 수정 가능 | 안 보임 (암호문) |
| 캐싱 | 가능 | 불가 |
| 프록시 일 | HTTP 해석·재작성 | 바이트 복사만 |

- 프록시가 HTTPS를 못 푸는 이유: TLS 키는 손님과 a.com만 가짐. 풀려면 가짜 인증서로 속이는 MITM이 필요함 → 브라우저 경고. 회사 보안 장비는 자기 인증서를 PC에 미리 깔아서 이걸 함.
- 한 연결이 두 단계로 바뀜:
  - 1단계 HTTP: CONNECT → 200
  - 2단계 TCP 파이프: TLS ClientHello부터 시작
  - 그래서 터널 뒤에는 keep-alive가 불가. 끝나면 연결을 닫음.
- 터널은 **아무 TCP 바이트나** 통과시킴(SSH, DB 프로토콜도) → 위험 → 실제 프록시는 보통 443만 허용함.
- 우리 코드 (`fproxy_tunnel`):
  - `poll`로 양쪽 소켓을 지켜보고, 받은 걸 반대쪽에 `send`.
  - 한쪽이 FIN을 보내면 반대쪽에 `shutdown(SHUT_WR)`.
  - 양쪽 다 끝나거나, 60초 무활동이거나, 서버가 종료되면 닫음.
- 사용: `curl -x http://127.0.0.1:8080 https://example.com/` → curl이 알아서 CONNECT부터 보냄.

### 터널의 워커 점유
- 터널 1개 = 워커 1개를 통째로 씀. 끝나는 조건은 양쪽 종료 또는 60초 무활동뿐.
- 브라우저는 HTTPS 연결을 오래 열어 둠 → 악의가 없어도 브라우저 하나로 터짐.
```
워커 16개 / 터널 16개 → 일반 GET은 큐에서 대기 → 큐 가득 → 503
```
- 수정: 동시 터널 수 상한 = 워커 수의 절반. 넘으면 503. (근본 해결은 터널을 epoll로 넘기기)

### DNS 해석 무제한 대기
- `getaddrinfo`는 블로킹이고 시간 제한 인자가 없음. DNS가 느리면 5~30초 멈춤. `-T`도 이 구간을 못 덮음.
- 공격: `GET http://느린도메인N/` × 워커 수 → 워커 전부가 `getaddrinfo` 안에서 잠듦.
- 수정:
  - 별도 detached 스레드에서 해석, 워커는 `pthread_cond_timedwait`로 최대 3초만 기다림 → 504.
  - 동시 해석 32개 초과 → 503.
  - 숫자 IP는 DNS를 거치지 않음.
  - `refs = 2`: 워커와 해석 스레드 중 늦게 끝나는 쪽이 free.

### 느린 목적지 (역방향 slowloris)
- 중계 루프가 `recv(-T)` → send를 반복함. **recv마다 -T가 새로 시작됨.** "조각 사이 최대 대기"만 있고 "전체 최대 시간"이 없었음.
```
목적지: Content-Length: 1000000, 9초마다 1바이트 (-T 10초 미만)
→ 타임아웃 안 걸림 → 100만 바이트 = 약 100일 → 워커 영구 점유
```
- 리버스 백엔드는 운영자가 정한 믿는 서버라 위험 낮음. 포워드 목적지는 인터넷 아무 서버 → 공격자가 자기 서버를 이렇게 만들면 끝.
- 수정:
  - 최저 평균 속도 1KB/s (처음 `-T` 동안은 봐줌). 포워드만 켜고 리버스는 끔.
  - 허용 시간 = grace + 받은 바이트/속도. 넘으면 중단.
  - 같은 구멍인 "1xx만 무한히 보내기"는 8개 상한 → 502.

### 죽은 백엔드 / passive health check
- 서버가 "A 죽었음"을 기억하지 않아서, 요청마다 A에 connect부터 다시 시도했음.

| A 상태 | connect 결과 | 손해 |
|---|---|---|
| 프로세스만 꺼짐 | 즉시 RST(refused) | 거의 없음 (~0.1ms) |
| 서버 다운, 방화벽이 패킷 버림 | 무응답 → 2초 뒤 타임아웃 | 요청 절반이 2초씩 늦어짐 |

- 죽은 백엔드가 여러 개면 개수 × 2초. 부하가 크면 워커가 `tcp_connect` 대기에 다 묶임.
- 수정 = **passive health check**:
  - 실패하면 `down_until = 지금 + 5초`로 표시하고, 그동안 라운드로빈에서 건너뜀.
  - 성공하면 0으로 되돌림.
  - 전부 죽음 표시면 표시를 무시하고 다 시도함 (회복 확인).
  - `atomic_llong` + `CLOCK_MONOTONIC`.
