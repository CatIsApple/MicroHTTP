## 핵심 개념 정리

### 소켓(Socket)
- 정의: 네트워크 통신 끝점 + 프로그램이 네트워크 쓰는 OS 인터페이스
- 비유: 전화기. IP = 집 주소, 포트 = 방 번호
- 리눅스에선 소켓 = fd → `read/write/close/dup2` 그대로 사용 가능 (CGI에서 stdout → 소켓 리다이렉트 가능한 이유)
- 종류: `SOCK_STREAM`(TCP, 연결형·순서 보장) / `SOCK_DGRAM`(UDP, 비연결·손실 가능)
- 서버 흐름: `socket → bind → listen → accept → read/write → close` / 클라: `socket → connect → ...`
- **듣는 소켓(listening)** 은 연결 요청만 받음. `accept()`가 클라이언트마다 **새 연결 소켓** 생성 → 데이터는 그쪽으로

### 소켓 내부 구현 (리눅스 커널)
```
int fd → task_struct.files_struct.fd테이블
  → struct file      (f_op = socket_file_ops: read/write/poll/close) "모든 건 파일" 층
  → struct socket    (type, state, ops = inet_stream_ops: bind/listen/accept) BSD API 층
  → struct sock → inet_sock(IP,포트) → inet_connection_sock(accept 큐, 재전송 타이머) → tcp_sock(seq/ack, 윈도우, 혼잡제어)
```
- `ops` = 함수 포인터 테이블 → C로 구현한 **다형성** (`bind()` syscall = `sock->ops->bind()`)
- 구조체 **상속식 중첩**: 첫 멤버가 부모 구조체 → 포인터 캐스팅으로 오감
- 버퍼: `sk_receive_queue`(도착 데이터), `sk_write_queue`(ACK 받을 때까지 보관), `sk_rcvbuf/sk_sndbuf`, `sk_wq`(잠든 프로세스·epoll 대기 큐). 패킷 단위 = `struct sk_buff`(skb)
- `write()` = 커널 송신 큐로 복사 후 즉시 리턴 → **성공 ≠ 상대 수신**
- `read()` = 수신 큐 → 유저 버퍼 복사. 비었으면 `sk_wq`에서 sleep
- epoll "읽기 가능" 통지 = 수신 큐에 데이터 생길 때 `sk_wq` 콜백
- 리스닝 소켓: **SYN 큐**(반쯤 연결) + **accept 큐**(handshake 완료, 크기 = backlog). `accept()`는 꺼내서 새 sock+socket+file+fd로 포장만 함
- 연결 구분 = 4-튜플 (내 IP, 내 포트, 상대 IP, 상대 포트) → 포트 80 하나로 다수 클라이언트
- 패킷 → read 경로: `NIC → 인터럽트/NAPI → skb → ip_rcv → tcp_v4_rcv(4-튜플 해시로 sock 찾기) → 순서정렬·ACK → sk_receive_queue → sk_data_ready()(깨움) → read() 복사`

### Windows Winsock/IOCP vs 리눅스
- 결론: 개념 같음(Winsock = BSD 소켓 본뜸). 차이 = API 표기 + I/O 모델
| 항목 | Windows | Linux |
|---|---|---|
| 타입 | `SOCKET` 핸들 | `int` fd |
| 초기화 | `WSAStartup/WSACleanup` 필수 | 없음 |
| 닫기 | `closesocket()` | `close()` |
| 에러 | `INVALID_SOCKET`/`SOCKET_ERROR` + `WSAGetLastError()` | `-1` + `errno` |
| 철학 | 소켓 ≠ 파일 | 소켓도 파일 |
- I/O 모델 (핵심):
  - IOCP = **완료 통지(Proactor)**: 버퍼 미리 넘김(`WSARecv` overlapped) → OS가 채움 → `GetQueuedCompletionStatus`로 "N바이트 다 읽음"
  - epoll = **준비 통지(Reactor)**: `epoll_wait` "읽을 수 있음" → 내가 `read()`
  - 리눅스에서 IOCP 대응물 = `io_uring` (완료 기반)
- 이번 서버 = 블로킹 + 반복(iterative) = IOCP 이전 단계. 발전 경로: `fork`/스레드 → `select`/`poll` → `epoll`
- Windows 커널도 `afd.sys`+`tcpip.sys`에 비슷한 버퍼·accept 큐 있음. 차이 = fd 통일 아님

### TCP
- L4 전송 계층. IP(best-effort: 손실·순서뒤바뀜·중복) 위에서 보장:
  - 연결 지향(3-way handshake) / 신뢰성(seq, ACK, 재전송) / 순서 보장(커널 재조립) / 흐름·혼잡 제어(rwnd, cwnd)
- **바이트 스트림**: send 1번 ≠ recv 1번 → `tcp_recv_request()`가 `\r\n\r\n`까지 반복 수신하는 이유
- 헤더 최소 20B: 포트×2, Seq(내 바이트 위치), Ack("여기까지 받음, 다음 줘"), Flags(SYN/ACK/FIN/RST/PSH/URG), Window(rwnd), Checksum, Options(MSS, WScale, SACK, Timestamp)
- 3-way handshake: `SYN(x)` → SYN 큐(SYN_RCVD) / `SYN+ACK(y, x+1)` / `ACK(y+1)` → accept 큐(ESTABLISHED) → `accept()`가 꺼냄
  - **handshake는 커널 혼자 처리. accept 전에도 이미 ESTABLISHED**
- 송신: `send()` 성공 = 커널 버퍼 복사 완료. 공간 부족 시 **일부만 복사하고 반환** → `tcp_send_all()` 반복
- 신뢰성: 누적 ACK, RTO(RTT 기반) 타임아웃 재전송, 중복 ACK 3번 → **Fast Retransmit**, SACK → 빠진 구간만 재전송
- 흐름 제어: Window = 내 수신 버퍼 남은 공간. 앱이 recv 안 하면 window 0 → 송신 측 멈춤
- 혼잡 제어: 송신량 = `min(rwnd, cwnd)`. Slow Start(지수) → Congestion Avoidance(선형) → 손실 시 감소. 리눅스 기본 **CUBIC**, BBR 선택 가능
- 4-way 종료: `FIN → ACK → (B: CLOSE_WAIT, 아직 송신 가능) → FIN → ACK`, 먼저 닫은 쪽 **TIME_WAIT (2×MSL, 리눅스 60초)**
  - 상대 FIN → `recv()` = 0 → 코드에서 `n == 0` = 상대가 닫음
  - 서버가 `close(cfd)` 먼저 → 서버에 TIME_WAIT 쌓임 → 재시작 시 `bind` `EADDRINUSE` → **`SO_REUSEADDR`**
  - 닫힌 연결에 write → RST → 또 write → **SIGPIPE**(기본: 프로세스 종료) → `SIG_IGN` + `EPIPE` 처리
- 커널 `tcp_sock` 필드: `sk_receive_queue / out_of_order_queue`, `sk_write_queue`, `snd_una, snd_nxt, rcv_nxt`, `snd_cwnd, ssthresh, srtt`, 타이머(재전송, 지연 ACK, keepalive, TIME_WAIT)
- 관찰: `ss -tanp | grep 8080` (LISTEN/ESTAB/TIME-WAIT), `sudo tcpdump -i lo -nn port 8080` → `[S]` → `[S.]` → `[.]` → 데이터 → `[F.]`

### 다른 프로토콜
```
L7 응용   HTTP, HTTPS, DNS, SMTP, SSH, FTP, WebSocket, gRPC, MQTT
L6~5 보안 TLS/SSL
L4 전송   TCP, UDP, QUIC, SCTP
L3 네트워크 IP(v4/v6), ICMP, ARP(L2~L3 걸침)
L2 링크   Ethernet, Wi-Fi
```
- 전송: TCP / UDP(연결 없음, 헤더 8B, **메시지 경계 유지**, DNS·게임·음성영상·DHCP) / QUIC(UDP 위 신뢰성+혼잡제어+TLS1.3, HTTP/3) / SCTP(메시지 단위·멀티스트림, 통신사망)
- TCP vs UDP: handshake 유무, 신뢰성·순서 보장 유무, 스트림 vs 데이터그램, `SOCK_STREAM`+listen/accept vs `SOCK_DGRAM`+`sendto/recvfrom`
- UDP 서버 = `socket(SOCK_DGRAM) → bind → recvfrom` (listen/accept 없음)
- QUIC 등장 이유: TCP **HOL blocking**(패킷 하나 빠지면 뒤 데이터 다 대기) + 커널 구현이라 변경 어려움 → UDP 위 사용자 공간 구현, 스트림 독립, 1-RTT / 재연결 0-RTT
- 네트워크 계층: IP(주소·라우팅, 신뢰성 없음), ICMP(`ping`, `traceroute`), ARP(IP → MAC, LAN 내)
- 응용: HTTP/1.1(TCP 80, **과제 대상**), HTTPS(TCP+TLS 443), HTTP/2(바이너리 프레임·다중화·헤더압축), HTTP/3(QUIC), WebSocket(HTTP Upgrade), DNS(UDP 53, 크면 TCP), DHCP(UDP 67/68), SSH 22, FTP 20/21, SMTP/IMAP/POP3 25/143/110, gRPC(HTTP/2), MQTT 1883, RTP(UDP, WebRTC)
- TLS: `HTTP → TLS → TCP → IP` = HTTPS. 암호화·무결성·서버 인증. TLS 1.3 = 1-RTT
- 과제 범위 = **HTTP/1.1 over TCP over IPv4**. TLS/HTTP2/3 불필요. 참고: Reverse Proxy 앞단 TLS termination(nginx) 실무에서 흔함

### 네트워크 계층(레이어)
- 왜: 문제가 너무 커서 역할별 분리, 각 층은 **바로 아래층 기능만 믿음** → 한 층 바꿔도 다른 층 그대로 (랜선 → Wi-Fi 바꿔도 HTTP 코드 불변)
- OSI 7계층 = 교과서 모델 / 실제 인터넷 = TCP/IP 4계층
| TCP/IP | 역할 | 예 | 단위 | 주소 |
|---|---|---|---|---|
| 응용 (OSI 5~7) | 무슨 내용 | HTTP, DNS, SSH, TLS | 메시지 | URL |
| 전송 (4) | **어느 프로그램**, 신뢰성 | TCP, UDP | 세그먼트/데이터그램 | **포트** |
| 인터넷 (3) | **어느 컴퓨터**, 경로 | IP, ICMP | 패킷 | **IP** |
| 네트워크 접근 (1~2) | 옆 장비까지 | Ethernet, Wi-Fi | 프레임/비트 | **MAC** |
- 택배 비유: 편지 내용(HTTP) / 받는 사람 이름 + 등기·일반(포트, TCP/UDP) / 집 주소(IP, 물류센터=라우터) / 구간별 트럭(MAC, 홉마다 바뀜)
- 캡슐화: 내려가며 헤더 앞에 붙임 `[Eth | IP | TCP | HTTP ... | FCS]`, 받을 땐 아래부터 뗌
- 내 코드 = HTTP 메시지만. socket API 경계 아래(TCP/IP/Ethernet 헤더, 재전송) = 커널+NIC

### 계층이 다른데 왜 TCP용/UDP용이 따로?
- 헷갈렸던 점: 계층 분리 → 아무 조합 가능? → 실제: **구현은 몰라도 되지만 아래층의 "보장"에 의존** → 설계 시점에 서비스 선택
  - HTTP/1.1: 빠짐없이 순서대로 가정(`Content-Length`만큼 읽기) → TCP
  - DNS: 짧은 질문·답, handshake 낭비 → UDP (크면 TCP)
  - RTP 화상통화: 늦은 데이터 무용 → 재전송 X → UDP
  - 비유: 계약서는 등기, 전단지는 일반우편
- 포트 체계도 별개: `TCP 53 ≠ UDP 53`, TCP 8080과 UDP 8080 서버 동시 가능 → "DNS: UDP/TCP 53"처럼 함께 표기
- 역다중화(demultiplexing): 각 헤더에 "다음 층" 필드 → `EtherType 0x0800 → IPv4`, IP `Protocol 1=ICMP, 6=TCP, 17=UDP`, 포트 → 프로그램
- 코드에서 선택: `socket(AF_INET|AF_INET6 = 3계층, SOCK_STREAM|SOCK_DGRAM = 4계층, 0)`

### IP Protocol 번호는 공식만 쓸 수 있나?
- 결론: **기술적으로 아무 번호 가능, 인터넷에선 사실상 TCP·UDP만 통과** (막는 건 규칙 아닌 중간 장비)
- 8비트(0~255), **IANA** 등록부 관리 = 약속. 1 ICMP, 6 TCP, 17 UDP, 41 IPv6 터널, 47 GRE, 50/51 IPsec ESP/AH, 89 OSPF, 132 SCTP, **253·254 실험용**(RFC 3692)
- Raw 소켓으로 직접 송신 가능: `socket(AF_INET, SOCK_RAW, 253)` + `sendto` (root/`CAP_NET_RAW`). 수신 측 커널은 무시, 같은 번호 raw 소켓 연 프로그램에 전달. `ping`도 이 방식(ICMP)
- 내 LAN·관리망에선 자체 4계층 프로토콜 가능
- 인터넷에서 막히는 이유: NAT(포트 위치 알아야 변환 → 모르는 프로토콜 버림), 방화벽(기본 차단), 로드밸런서·DPI(TCP/UDP만 해석) → **프로토콜 경직화(ossification)**
- 사례: SCTP — 좋지만 NAT 통과 못 해 통신사 내부망만. QUIC — **UDP(17) 위에 만들어** 통과 + 헤더 암호화로 재경직화 방지 → 새 전송 프로토콜은 "UDP 위에" 가 정석
- 포트는 더 자유: 0–1023 well-known, 1024–49151 registered, 리눅스 1024 미만은 root 필요. 80 = HTTP 기본값 약속일 뿐, `:8080` 가능

  - `SIGPIPE` → `SIG_IGN`, send 실패는 `EPIPE`로 처리
  - BACKLOG 128, 수신 버퍼 8192
- 에러 → 원인 → 해결:
  - Makefile `asan` 타깃이 `CFLAGS`를 커맨드라인으로 덮으면 `CFLAGS += -Iinclude` 무시됨 → include 경로를 `CPPFLAGS`로 분리
  - `wsl --cd /mnt/d/...` 를 Git Bash에서 호출 시 `ERROR_PATH_NOT_FOUND` → MSYS 경로 변환 문제 → 스크립트 파일로 만들어 `MSYS_NO_PATHCONV=1 wsl -d Ubuntu -- bash <script>` 실행
- 테스트 결과: curl `200 OK` / nc 분할 송신 재조립 OK / 데이터 없는 연결("closed without data") OK / 연속 5회 OK / 포트 중복 `bind: Address already in use` exit 1 / 잘못된 포트 usage 출력 / Ctrl+C(SIGINT) → "shutdown complete" exit 0 / `make asan` 빌드 OK
